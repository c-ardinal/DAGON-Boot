この文書は[lifecycle-events.mdの5.5節](/explanation/lifecycle-events/#55-マイコンの識別とコンパイル済の構成-要件と実行可能なモデル)が実行可能なモデルに委任した形式の規範仕様です。対象はマイコンの識別とコンパイル済構成のノードのレイアウトです。ブートローダの試行のセル（5節）と状態ログの面と記録（6節）も規定します。ここにある形式は例外なく`crates/dagon-retained-model`が証明済のものです。形式の変更時は、最初にモデルを変更し、モデルのテストで決定します。

モデルはホスト専用で、リリースしません。形式のコーデックはモデルのトレイトです（`codec::Codec`。マイコンの識別は`identity::Identity`）。本番のコーデックはこれらのトレイトを実装し、モデルのハーネスで試験します。コンパイル済の構成は`dagon_format::topology`、試行のセルは`dagon_core::bootcore`、識別は`dagon_format::header::McuId`です。

```
cargo test -p dagon-retained-model                       # 10^4 scenarios per world, fixed cases
cargo test -p dagon-retained-model --release -- --ignored # 10^6 scenarios per world
DAGON_MODEL_SCENARIOS=<n> DAGON_MODEL_SEED=<seed>         # override count and base seed
```

失敗したシナリオは、そのシード、構成、そして同一の性質でなお失敗する最小の一覧まで縮小した操作の一覧を表示します。そのケースを回帰テストとして`tests/fixed.rs`に追加します。

## 1. 故障モデル

証明がハードウェアについて仮定する内容と、注入する故障です。

- **ストア。** 保持メモリへの書込は、プログラム順にバイト単位のストアで実施します（1回の書込ステップの間にデータメモリバリアを挟んだvolatileのストア）。幅の広いストアは、異なる2個のステップのバイトを混在させない場合に使用可能です。32ビット単位だけのレジスタファイルは、ステップの隣接バイトを既存の値で再書込します。実行はどのバイトの後にも停止する場合があります（リセットか電断）。モデルは全書込の全バイトの後にこの停止を注入します。
- **リセット**は保持のバイトを残存させます。**電断**が残存させる対象は位置ごとに異なります（5）。
- **NORフラッシュ**は`0xFF`に消去し、ビットを1から0に書込します。中断された消去は、先頭の一部を消去済に、残存部分を旧値かランダムな値のままにします。中断された書込は、先頭の一部を書込済にします。どのバイトも（書込が中断されたコミットバイトも同様に）、次回の消去か書込まで、読出のたびに同一の値になります（弱いビットはありません）。一部だけ書込したバイトで異なる値を返却する場合があるフラッシュでは、マイコン定義のコードが、2回の読出の値が一致するまでコミットバイトを再読出する必要があります。
- **外来のバイト。** どのバイトも、その形式の書込側ではないもの（同一段階の別レイアウトの書込側や、故障）に上書きされる場合があります。モデルは全領域にランダムなバイトを注入します。

以下の保証は例外なく構造的なものです。確率ではなく、どの中断点でも成立します。

## 2. マイコンの識別

`identity(id)`は、`SHA-256("dagon-mcu/" ‖ id)`の最初の8バイトをリトルエンディアンのu64にした値です。`id`はマイコン定義の`id`です。識別の応答（HELLO）は下位16ビットを保持し、他の箇所は64ビット全部を保持します。識別を保持する箇所は`image-header`、`identity-reply`、`version-0x06`、`topology-node`です（モデルの`identity::CARRIERS`です。テストがこの行と照合します）。定義の読込は、いずれかの箇所の幅で識別が一致する2個の定義を、両方のidを提示して拒否し、その箇所の幅で全ビットがゼロか全ビットが1の識別を拒否します。読込したどの定義とも完全には一致しない識別のデバイスは、不明と表示します。数値のマイコンの表はありません。

## 3. コンパイル済の構成

### 3.1 本体（`topology-bin` 3）

先頭は32バイトです。マジック`DGTP`、レイアウトu16 LE（3）、ノード数（1から`MAX_NODES`）、リンク数（≤ `MAX_LINKS`）、オフセット8に全体のサイズu32 LE、オフセット20に制約数（≤ `MAX_CONSTRAINTS`）、他のバイトはゼロです。その後に以下の要素があります。

- ノードは各40バイト: 番号、役割、ゼロ2バイト、ポートの種類、試行の上限、待受時間ms u16 LE、マップのid、復旧の段階[3]、順番、ゼロ3バイト、オフセット16にターゲットのタグ[16]、オフセット32にマイコンの識別u64 LE。
- リンクは各20バイトで、イメージツールにおけるリンクのレイアウトです。向きはなく、2個の端それぞれにノード、ポートの番号、アドレスがあります。
- 制約は各16バイトで、マニフェストの制約のレイアウトです。

正規の形式: ノードの`index`は位置と同一、リンクの端はノードの順、リンクは端のノードの順、予約のバイトはゼロです。旧レイアウト（2は32バイトのノードと16ビットのマイコン番号）は読込しません。デコーダは再符号化して比較します。

## 4. 性質

モデルは全シナリオの全操作の後にこれらを確認します。`tests/fixed.rs`の固定のケースは保護対象の性質を名称で明示します。

| Id | 性質 |
|---|---|
| P12 | 識別はidの純粋な関数です。衝突はどの箇所の幅でも拒否します。不明なものを一致とは判定しません。 |
| K1 | コーデックは、符号化した値を同一の値に復号します。 |
| K2 | 復号可能なバイト列は、原因の故障に関係なく、再符号化の後も同一の値に復号します。 |
| K3 | 正規のコーデック（コンパイル済の構成）では、復号可能なバイト列はその値の符号化と完全に一致します。損傷したバイト列は拒否するか、別の完全な値として復号します。 |

K1からK3は本番のコーデックで実行します。注入する故障は、外来のバイト（位置は任意）、切断（残存するバイト数は任意）、末尾へのバイトの追加です。試行のセルは正規ではありません。2個のストアの間で中断されたセルは旧値のワードを1個保持し、計数の対象です（5）。

## 5. ブートローダの試行のセル

stage0は待機中のブートローダの起動回数を、フラッシュではなく2個の保持のワードで計数します。この方式ではstage0にフラッシュの書込側がなく（stage0には書込しないので、保持するコードを最小限にします）、書込側の不具合が原因でstage0が何も起動しない状態になることはありません。`dagon_core::bootcore`がコーデックで、そのテストが証明です。

| マイコン | 位置 | 残存する対象 | 消失する対象 |
|---|---|---|---|
| RP2040 | ウォッチドッグのSCRATCH0、SCRATCH1（ブートROMはSCRATCH4-7を使用します） | 電源投入とRUNピン以外の全リセット | 電源 |
| STM32F401RE | RTCのバックアップレジスタBKP0R、BKP1R | ウォッチドッグによるリセットも対象とする全システムリセット | バックアップドメインの電源（VBATを接続している構成ではVDD） |

待機中のイメージ`p`の起動`n`（最大15）の値は、1個のワード`0xB7 << 24 | p.digest16[0] << 16 | p.digest16[1] << 8 | n << 4 | (!n &
0xF)`で、両方の位置にストアします。ワードが`p`の計数対象になるのは、タグ、ダイジェストのバイト、回数の検査（下位4ビットは回数の補数）が成立する場合だけです。セルは2個のワードのうち回数の最大値を計数し、`[0, 0]`はクリアされたセルです。ワードはそれぞれ1回のストアなので、リセットが2個のストアの間に発生する場合があります。その場合、新規ワード1個と旧ワード1個でも新規の起動を計数し、計数が減少することはありません。ランダムなワードが一致する確率は2^-28で、一致してもstage0がそのコアを早期に断念するだけです。

実行可能なモデルは`dagon-retained-model`の`world_trial`です。本番のコーデックと、stage0とブートローダの規則（`bootcore::choose`、`settle`）を、2個のワード上で実行します。新規コアを正常か破損として待機状態にし（破損したコアはstage0の検査に合格し、自身の検査に失敗します）、セルへのどのストアの後にも（セルの検査のストアも対象で、マイコンの順に、ワード0、次にワード1）、リセットか電断（セルはクリアかランダムになります）を挿入します。シードのシナリオを`cargo test`で実行し、完全なプロファイルではシナリオ数を大幅に増加して実行します。その性質を、全操作の後に確認します。

| Id | 性質 |
|---|---|
| C1 | 2回の電断の間に、待機中のコアを試行として起動するのは最大`max`回です。 |
| C2 | 追加の故障がなければ、最大`max + 1`回のブートで試行が終了します。待機中のコアはなく、あるコアが動作します。 |
| C3 | 破損したコアが確定することはありません。 |

マイコン定義のスイープ（`a_power_cut_at_every_flash_step_leaves_a_bootable_core`）は、フラッシュ側を追加します。書込の全フラッシュ操作での電断で、状態ログのコンパクションも対象です。

stage0の判定は、Kaniの証明（`crates/dagon-core/src/proofs.rs`）が全入力で検査します。セルの性質（計数は15以下、2個のストアの間で中断した書込で計数が減少しない、別イメージのセルは計数対象外）、計画と決着の規則、そしてフラッシュと保持メモリの全内容に対して、状態ログの読込とstage0の判定（`bootcore::start`）の組立がパニックしないことです（イメージの検査は任意の結果に置換します）。ノード全体の組合せは、F401のパッケージの網羅探索（`targets/mcu/stm32f401re/tests/explore.rs`）が検査します。方法は[DAGON自体の開発: 形式検証](/explanation/repository/#形式検証)に記載しています。

書込した値を一切保持しないセルは、起動したブートローダとアプリが実行する`bootcore::cell_holds`が検出します。そのようなノードはブートローダを受信せず、その状態を検出した待機中のコアは自身でロールバックします。

回数を保持するワードがあるセルは、stage0が書込したセルなので保持が成立しており、検査はそのセルに何も書込しません。何も計数していないセルにだけ、検査用の値（セルのワードが使用しない値）と検査前の値を、ワードごとに書込し、それぞれ再読出します。そのため、検査中のリセットで、セルが計数する起動が減少することはありません。

### 5.1 アプリの引渡し

実行中のESPイメージは自身の領域にアプリを割当不可能なので、ESP32-S3ではstage0がアプリを起動し、ブートローダはリセットで起動を依頼します。依頼と結果は試行のセルと同一の2個のワードに格納し、セルは常にタグの異なる1個の値だけを保持します。

| タグ | 値 | 書込元 | 有効の条件 |
|---|---|---|---|
| `0xB7` | 試行の回数（上記） | stage0 | どちらかのワード |
| `0xB8` | `START_APP`: 固定値`0xB8C33C5A`の2回 | ブートローダ | 両方のワード |
| `0xB9` | `app_result`: `0xB9 << 24 \| 0x5A << 16 \| 0xA5 << 8 \| c << 4 \| (!c & 0xF)`の2回（`c`は1: `NoImage`、2: `Rejected`） | stage0 | どちらかのワード |

ブートローダは自身の試行の決着後に`START_APP`をワード0、ワード1の順に書込してリセットします。stage0はブートローダの選択に先行して依頼を受理し（`take_request`）、ワード0からセルをクリアし、クリアを再読出で確認した場合だけアプリの判定を1回実行します。判定がアプリを起動しない場合は結果を書込し、確定済のブートローダだけを起動します。そのブートローダは結果を読込し（`hand_off`）、セルをクリアし、イメージかログの選択が変化するまで復旧モードを継続します。

依頼は両方のワードが一致する場合だけ有効なので、書込中や受理中のリセット後に依頼は残存しません。そのため1個の依頼で判定を実行するのは最大1回で、未完了の書込では判定を実行しません（ブートローダが次回の起動で再度依頼します）。結果はブートローダの依頼を抑止するだけなので、どちらかのワードで有効です。リセットで結果が消失しても、判定が1回増加するだけです。依頼と結果は試行の回数として計数されず、相互に誤読されません（Kaniの証明`the_cell_values_never_read_as_each_other`）。

実行可能なモデルは`dagon-retained-model`の`world_hand_off`です。本番の規則（`take_request`、`app_result`、`hand_off`、`cell_holds`、確定済コアに対する`choose`のセル）を、全ストア（依頼、受理、結果、確定済コアの起動、セルの検査、結果のクリア）の直後にリセットか電断を挿入して実行し、アプリを正常、不在、破損に変更します。全操作の後に確認する性質は以下のとおりです。

| Id | 性質 |
|---|---|
| H1 | stage0がアプリの判定を実行するのは、ブートローダが完全に書込した依頼に対してだけで、各依頼で最大1回です。 |
| H2 | 追加の故障がなければ、1回のブートは、アプリが正常ならアプリの動作で、それ以外ならブートローダの復旧モードで終了し、判定は最大2回です。 |
| H3 | ブートローダが復旧モードを継続するのは、その時点のアプリに対してstage0が書込した結果がある場合だけです。 |

主張の限界: 各位置が、列挙したリセットをまたいで値を維持することは、ベンダーが文書で明示している動作です。

## 6. 状態ログの面と記録（`state-log` 1）

状態ログは、イメージのスロットの記録を収容します。この節は面と記録の規範です。面、面ヘッダ、スロットの記録の畳込は`dagon_format::statelog`と`dagon_core::log`の定義です。

ログは交互に使用する2面です。面は32バイトの面ヘッダと、後続の32バイトの記録で構成し、消去済のバイトは`0xFF`です。有効な面のうち世代が最大の面が使用中の面です。記録は順番に畳込し、畳込は最初の消去済記録か、最初のCRC不一致記録で終了します。

| オフセット | サイズ | 欄 |
|---|---|---|
| 0 | 1 | 種別: `0x01`から`0x7F`はスロットの記録、`0x80`から`0xFE`は予約、`0xFF`は消去済 |
| 1 | 3 | 種別ごとの欄 |
| 4 | 4 | `seq`: 連番、リトルエンディアン。畳込は連番を使用しません |
| 8 | 20 | 種別ごとの欄 |
| 28 | 4 | バイト0から27のCRC-32（ISO-HDLC） |

記録は、使用中の面にある最初の消去済記録へ、その32バイト全部の消去を確認した後に追記します。面が満杯の場合、面の末尾がCRC不一致記録の場合、この確認が不成立の場合、追記は事前にコンパクションを実行します。コンパクションは他方の面を消去し、畳込結果を複写し、世代に1を加算した面ヘッダを最後に記録します。複写は畳込結果の全欄（確定済、待機中と試行回数、差戻し済のイメージ、最後の差戻しの理由）を保存し、複写した記録の畳込は複写元の畳込結果と同一です（`LogState::carry`。網羅試験`carry_is_exact`とKaniの証明`compaction_carries_the_whole_state`が検査します）。その面ヘッダが完成するまで、旧面が有効です。読出側は、未知の種別の記録を無視します。

両面の面ヘッダが無効の場合（両面の破損）は、ブートローダがスロットから状態ログを再作成します（`dagon_core::boot::rebuild`、`Log::create`）。各APPスロットのイメージに起動時と同一の検査を実行し、合格したイメージを記録します。2個が合格し版が相違する場合は、旧版をPROVISION、新版をSLOT_PENDINGで記録します。新版は試行で起動し、不合格の場合は旧版に復帰します。版が同一の場合は、スロットAだけをPROVISIONで記録します。1個だけが合格した場合は、SLOT_PENDINGだけを記録します。どのログも確定していないイメージは試行でだけ起動し、不合格の場合は復旧モードに移行します。合格が皆無の場合は何も書込しません。再作成は面0を消去し、記録を書込し、世代1の面ヘッダを最後に書込します。面ヘッダの完成前の電断では両面が無効のままなので、次回の起動で再度作成します。ブートローダの記録と同一の面を共用する構成（F401）では、両面の破損でブートローダの記録も消失し、stage0がブートローダを起動しないので、ROMローダで復旧します。
