この文書は[lifecycle-events.mdの5.5節](/explanation/lifecycle-events/#55-ブート記録マイコンの識別コンパイル済みの構成-要件と実行可能なモデル)が実行可能なモデルに任せている形式の、規範となる仕様です。対象はブート記録、ロックアップヒューズ、マイコンの識別、コンパイル済みの構成のノードのレイアウトと置き換えです。ここにある形はどれも`crates/dagon-retained-model`が証明しているものです。形を変えるときは、まずモデルを変え、モデルのテストで決めます。

モデルはホスト専用で、リリースしません。各形式のコーデックはモデルのトレイトです（`RecordCodec`、`FuseCodec`、`BodyCodec`）。本番のコーデックは同じトレイトを実装し、同じハーネスで動きます。そのため、配布するコーデックと証明がずれることはありません。

```
cargo test -p dagon-retained-model                       # 10^4 scenarios per world, fixed cases
cargo test -p dagon-retained-model --release -- --ignored # 10^6 scenarios per world
DAGON_MODEL_SCENARIOS=<n> DAGON_MODEL_SEED=<seed>         # override count and base seed
```

失敗したシナリオは、そのシード、構成、そして同じ性質でなお失敗する最小の一覧まで縮めた操作の一覧を表示します。そのケースを回帰テストとして`tests/fixed.rs`に足します。

## 1. 故障モデル

証明がハードウェアについて仮定することと、注入するものです。

- **ストア。** 保持メモリはプログラムの順にバイトのストアで書かれます（1回の書き込みのステップのあいだにデータメモリバリアを挟んだvolatileのストア）。幅の広いストアは異なる2つのステップのバイトを合わせないときに使えます。32ビット単位だけのレジスタファイルは、ステップの隣のバイトをいまの値で書き直します。実行はどのバイトの後でも止まることがあります（リセットか電断）。モデルはすべての書き込みのすべてのバイトの後にこの停止を注入します。
- **リセット**は保持のバイトを残します。**電断**は、定義の`[boot.record] survives`が宣言するとおりです。`reset-random`（バイトはランダム、SRAM）、`reset-cleared`（バイトはゼロ、レジスタ）、`power`（バイトは残る、バッテリバックアップ）です。
- **NORフラッシュ**は`0xFF`に消去し、ビットを1から0に書き込みます。中断された消去は先頭の一部を消去済みに、残りを古いかランダムなままにします。中断された書き込みは、先頭の一部を書き込み済みにします。どのバイトも、書き込みが中断されたコミットバイトを含め、次の消去か書き込みまで、読むたびに同じ値になります（弱いビットはありません）。一部だけ書かれたバイトで違う値を返すことがあるフラッシュでは、マイコンの定義のコードが、2回の読み出しが一致するまでコミットバイトを読み返す必要があります。
- **外来のバイト。** どのバイトもその形式の書き手ではないもの（同じ段階の別のレイアウトの書き手や、故障）に上書きされることがあります。モデルはすべての領域にランダムなバイトを注入します。

2つの保証は確率的です。ランダムなバイトが有効なエントリや記録として受け付けられるのは、8ビットのコミット値とCRC-32の偶然の一致のときだけです（スロットごとに最大2^-40）。構成の保存はさらにSHA-256の一致も求めます。新しいブート記録のシーケンスが以前のシーケンスの番号とタグを繰り返す確率は、エントロピーワードの最小エントロピーがkビットのとき約2^-kで（2.3）、これが問題になるのは、読み手が前回のリプレイで見た識別子に対してだけです。下のほかの保証はどれも構造的なものです。確率ではなく、どの中断点でも成り立ちます。

## 2. ブート記録（`boot-record` 1）

この文書のバイトの範囲は両端を含みます。「バイト1から23」は、オフセット1、2、…、23の23バイトです。

### 2.1 配置

マイコンの定義の`[boot.record]`は、領域（最大`RECORD_MAX` = 4096バイト）、書き手ごとに1つのリングをバイトの範囲としてブートの順に、そしてエントロピーワード（2.3）を宣言します。リング0はDAGONの最初の段階（マイコンにあれば、リセットの後で最初に動く小さなプログラムであるstage0）のもので、リング1は次の段階のもの、以下同じで、書き手は最大16です。リングは`bytes / 28`個のエントリのスロットを持ち、2から256個です。リングは重ならず、領域の中にあります。レジスタファイルの予約アドレスは、どのリングの外にもあります。同じ定義がすべてのイメージの`memory.x`に届きます。

### 2.2 エントリ

28バイト、リトルエンディアンです。

| オフセット | 大きさ | 欄 |
|---|---|---|
| 0 | 1 | コミット: `0xB1`はコミット済み。ほかの値はレイアウト1のエントリではありません |
| 1 | 1 | フラグ: ビット0 `start`（書き手の実行の最初のエントリ）、ビット1 `epoch`（新しいシーケンスの最初のエントリ）、ビット2-3はゼロ、ビット4-7 `opener` |
| 2 | 1 | 書き手の`event`の形式番号 |
| 3 | 1 | イベントの種類 |
| 4 | 4 | `eseq`: 書き手の連番 |
| 8 | 4 | `boot`: このブートを開始した段階の最初のエントリの`eseq` |
| 12 | 4 | `boot tag`: ブートを開始した段階のシーケンスのタグ |
| 16 | 4 | `tag`: この書き手のシーケンスのタグ |
| 20 | 3 | ペイロード（イベントの短い形） |
| 23 | 1 | ゼロ |
| 24 | 4 | `[1, writer index]`とそれに続くバイト1から23に対するCRC-32（ISO-HDLC） |

エントリが有効なのは、コミットバイトが`0xB1`で、予約のビットとバイトがゼロで、CRCが一致するときです。CRCはレイアウトの番号と書き手の番号を束ねるので、別のレイアウトのエントリや、別の書き手のリングにあるエントリは、決して有効になりません。

**追記**は、この順です。バイト0に`0x00`をストアする。バイト1から27をストアする。バイト0に`0xB1`をストアする。2度ストアするのはコミットバイトだけで、それも自分の追記の中だけです。最初のストアは、ほかのバイトが変わる前にスロットを無効にし、最後のストアは、すべてのバイトがそろった後でスロットを有効にします。どこで中断された書き込みでも、有効なエントリを上書きしている場合を含め、失うのは最大でそのエントリだけで、読み手が受け付けるものが2回の書き込みから作られることはありません。ほかの欄を書き直すことはありません。

### 2.3 書き手

書き手の番号は**シーケンス**を作ります。シーケンスは空のリングで始まり、すべてのエントリに1つのタグを持ちます。段階は実行ごとに1度書き手を開き、**自分のリングだけ**を読みます。

1. すべてのスロットを1度ずつ解読します（スロットごとにCRC 1回）。いちばん新しいエントリは、後ろ2^24の連番以内に有効なエントリがいちばん多い有効なエントリです（同数なら上のスロット）。書き手が埋めたリングでは、一周をまたいで最大の`eseq`になります。
2. **破損していないリング。** リングが破損していないのは、書き手自身の追記が残すものとぴったり同じときです。すべてのスロットが有効で、番号がいちばん新しいものからスロットごとに後ろへ下がるか、最初の一周の前で、スロット0から*p*（いちばん新しいもの）までが有効で、スロット0の`epoch`のエントリまで下がり、それより後のスロットがすべてゼロのときです。
3. **続ける。** いちばん新しいエントリがあるとき、次の追記は次のスロット（`slots`の剰余）に、そのエントリのタグで行います。`eseq`は、リングが破損していないなら最新 + 1、破損しているなら最新 + `slots`です（書き手が書いていないバイトがエントリを壊していて、それが手元の最新より新しかった可能性があるためです。この番号の飛びで壊れたエントリを越え、読み手はそれをギャップとして示します）。
4. **新しいシーケンス。** 有効なエントリが無いとき、書き手はリングのすべてのバイトにゼロをストアし、スロット0に`epoch`で追記します。`eseq`は、領域全体の生のバイトのFNV-1a-32で、基底は`0x811C9DC5` XORエントロピーワードです。タグは同じバイトのFNV-1a-32で、基底は`0x050C5D1F` XOR左に16回転したエントロピーワードです。
5. **ブート。** 前の段階からの引き渡し（2.4）が、このレイアウトで有効で、より前の書き手を示すときは、それを使います。それ以外のときは、この段階が自分でブートを開始します（`opener` = 自分の番号、`boot` = 最初のエントリの`eseq`、`boot tag` = 自分のタグ）。ブートを開始する段階は、引き渡す前に最初のエントリ（`entry`イベント）を追記します。
6. 実行の最初のエントリは`start`を持ちます。

書き込みの位置は定義の定数と、書き手が自分のリングで検証したエントリからしか来ません。そのため、外来のバイトがストアをリングの外に向けることはできません。開始の値をわざとCRCにしていないのは、CRC-32で守られたエントリの領域に対するCRC-32は、その中身にほとんど依存しないからです。

**エントロピーワード。** マイコンの定義はエントロピーワードの出所を宣言します（`[boot.record] entropy`）。領域だけでは以前の状態に戻ることがあります（`survives = reset-cleared`の電源投入後のすべてゼロや、同じ段階の別のレイアウトの書き手がリングを消した後）。そのため、このワードは新しいシーケンスごとに最小エントロピーを16ビット以上持たなければなりません。これを満たすものならどれでも有効です。ハードウェアの乱数生成器、リングオシレータのランダムなビットの繰り返しサンプル、低速と高速のオシレータの周期のキャプチャ、内部センサのADCの繰り返し変換の下位ビットなどです。出所の無いマイコンには、ブート記録はありません。

**stage0の上限。** 書き手は記録するすべての段階で動き、stage0も含まれます。そのため、その時間はその段階の時間の上限（stage0では`stage0.max_ms`）に数えます。開くときにスロットごとのCRC 1回、新しいシーケンスでリングの消去、イベントごとに追記1回です。stage0はブートごとにわずかなイベントしか記録しません。stage0のリングは2から4スロットで足ります。

### 2.4 引き渡し

段階はジャンプのときに4つの32ビットのレジスタでブートの識別を次の段階に渡します。保持メモリは決して使いません（ハングした前のブートが古い値を残すことがないように）。

| ワード | 値 |
|---|---|
| 0 | `0x52424744`（`DGBR`） |
| 1 | `boot` |
| 2 | `boot tag` |
| 3 | ビット0-7 `opener`、ビット8-15記録のレイアウト、ビット16-31はワード0から2とワード3のビット0-15（リトルエンディアン）に対するCRC-32の下位16ビット |

受け取る段階がこれを使うのは、マジック、検査、レイアウトが一致し、`opener`が自分の番号より小さいときだけです。別のレイアウトの正しい形の引き渡しを受け取った段階は、それをそのまま次に渡します（途中に別のレイアウトの段階が1つあっても、つながりが切れないように）。それ以外のときは、自分のブートを渡します。この記録より古い段階は、次の段階が自分でブートを開始するに任せます。

### 2.5 読み手

エージェントは起動時に1つのレイアウトで領域を1度読みます（書くことはありません）。書き手ごとに、最新から2^24以内の有効なエントリを古い順に読みます。実行は各`start`のエントリか、ブートの変わり目で始まります。書き手ごとに**範囲**（`from` = 手元でいちばん古い`eseq`と、そのエントリが`epoch`を持つかどうか。持つなら、このシーケンスにそれより前のものはありません）と、欠けた連番の範囲ごとの**ギャップ**を示します（番号の飛びの後では、ギャップの中の番号は使われなかったことがあります）。有効なエントリが無い書き手は**空**と示します。

ブートはすべての書き手の実行の順を合わせて順序づけ、同じ段階が開始したブートは番号で順序づけます。

- ブートを開始した段階のいまのシーケンス（手元の最新のエントリのタグ）のブートは、ほかのどのシーケンスのブートよりも新しいものです。
- いまのシーケンスの中では、手元の最新のエントリから後ろへの距離で順序づけます（それより2^24先までのブートは新しいものです。そのエントリは壊れています）。
- ほかのシーケンスの中では、離れ方が2^30未満のときに連番の順で順序づけます（番号で順序づけるのは、どの書き手の実行の順でも関係づけられない組だけです）。
- ほかの2つのシーケンスのブートや、ほかのシーケンスで2^30以上離れたブートは、番号では順序づけません。

読み手は、新しいブートを古いブートより先に報告することはありません。順序づけられない組は、不確かと印を付けます（両方のブートに`uncertain`）。そのような組は次のどちらかです。

- どの書き手の順でも関係づけられない別々の段階が開始したブート（2.7）
- ブートを開始した1つの段階の、もういまのシーケンスでないシーケンスのブート

リプレイ: ブートは古い順、ブートの中では書き手の順、次にシーケンスの順です。各イベントはそのカタログのイベントとして`replayed: true`と識別子`(writer, tag, eseq)`を付けてリプレイします。ブートは`(opener, boot, boot tag)`です。欠落の報告も一緒にリプレイします。`plan`、`commit`、`self_check`、`confirm`はこの記録を読みません。`app.trial_started`と`app.rolled_back`は状態ログから来ます。

### 2.6 受信側

リプレイは少なくとも1回です。手元のすべてのエントリを、起動のたびにリプレイします。あるリプレイに無かった識別子は二度とリプレイされません。そのため、受信側は`(layout, writer, tag, eseq)`を読んだ前回のリプレイと比べて重複を除けばよく、それより古いものを持つ必要はありません。書き手は以前に追記した識別子を追記しません（2.3の手順3は壊れたエントリを飛び越えます。新しいシーケンスには新しいタグがあります）。そのため、2.7の限界の中で、新しいイベントを見たものと取り違えることはありません。`from`が受信側がその書き手から最後に見た識別子より後である範囲、ギャップ、`epoch`の開始は、そのあいだのエントリの欠落です。

### 2.7 主張の限界

- **2^32の一周。** 識別子が繰り返すのは、1つのシーケンスで書き手が2^32回追記した後だけです。1つの書き手の追記で2^32 − `slots`回より離れた2つのリプレイを読む受信側は、新しいエントリと同じ番号の古いエントリを区別できません。同じように、ブートを開始した段階の追記で2^32 − `slots`回より古いブートへの、後の段階のつながりは、最近のブートとして置かれることがあります。また、ブートを開始した段階がもう持っていないシーケンスの2つのブートが、その追記で約3·2^30回以上離れていて、どの書き手の実行の順でも関係づけられないときは、順序を間違えることがあります（2^32をまたぐ連番の順では、そのような組は逆向きに2^30未満の離れ方に見えます。2.5）。
- **繰り返しの破壊。** 書き手が書いていないバイトが、前回から`slots`個のエントリを追記する前に、最新のエントリをまた壊すと、2.3の番号の飛びでは足りず、書き手が壊れたエントリの番号を使い回すことがあります（その欠落は示されません）。最初の一周のあいだにスロットをすべてゼロにする破壊は検出しません。
- **ブートを開始する段階の交代。** 1つの書き手が読み手のレイアウトでの記録をやめ、また始めるとき（あいだに古いか別のレイアウトのstage0があるとき）、それが開始したブートと、次の段階が自分で開始したブートは、互いに順序づけられません。読み手はこれを不確かと印を付けます。順序づけるには両方の段階が書くカウンタが必要で、書き手の独立性がそれを許しません。
- **分かれたブート。** チェーンの途中にこの記録より古い段階があるとき、または1つのブートに2つの記録のレイアウトの段階があるときは、後の段階がブートをもう一度開始することがあります。そのブートは2つとしてリプレイされます。

### 2.8 VERSION

0x20（ブート記録の要約）: `layout u8, boots u8, flags u8`（ビット0: あるブートが不確か。ビット1: 欠けが示されている、つまりある書き手にギャップか、いちばん古いエントリが`epoch`の開始でない範囲がある）、続いていちばん新しいブートの`opener u8, boot u32 LE, boot tag u32 LE, count u8`と、そのブートの書き手ごとの最後のエントリを`writer u8, format u8, kind u8,
payload[3]`として。0x21は領域を生で返します。`offset u16`と、最大`RECORD_PAGE(link)`バイトです。ホストがページをつなぎ、この読み手で解読します。

### 2.9 バージョン付け

レイアウト*n*（1から15）は`0xB0 | n`でコミットし、そのCRCは*n*を初期値にします。15を超えるレイアウトは、`0x00`でも以前のどのレイアウトの値でもないコミット値を取り、ここに挙げます。読み手は、最初のバイトが別のレイアウトのコミットであるスロットを数え（刻みが違うところでは近似の数です）、別のレイアウトの記録があることを報告できますが、解読はしません。書き手のイベントの符号化は、その書き手の`event`の番号とともに変わり、番号は各エントリにあります。

## 3. ロックアップヒューズ（`boot-record` 1）

### 3.1 セル

サンドボックスの呼び出しを動かすイメージの種類ごとに、セルが1つあります。ブートローダのセルとアプリのセルです（アプリとリレーのレイヤーは共有します。コアごとに、開いているサンドボックスの呼び出しは最大1つです）。セルは有効化のスロットとそれに続く記録のスロットです（`[boot.record] fuse`が、記録の隣に両方のセルとそのスロットの数を宣言します）。セルにストアするのは、そのセル自身のレイヤーだけです。どのレイヤーの起動も、すべてのセルを読みます。

### 3.2 ヒューズのid

`SHA-256("dagon-fuse/1" ‖ layer u8 ‖ slot u32 LE ‖ image header digest
[32] ‖ chain index u32 LE ‖ artifact SHA-256 [32])`。欄の幅は固定なので、異なる2つの呼び出し箇所が同じ入力になることはありません。スロットや拡張の数に上限はありません。拡張の新しいビルドや新しいイメージは、新しいidです。

### 3.3 記録

40バイトです。

| オフセット | 大きさ | 欄 |
|---|---|---|
| 0 | 1 | 印: `0xA1`有効化、`0xA2`トリップ、`0xA3`クリアの要求、`0xA4`ロックアップの判定、`0xA5`正常の判定、`0xA6`クリア済み。ほかの値は空き |
| 1 | 1 | レイヤー |
| 2 | 2 | ゼロ |
| 4 | 32 | ヒューズのid |
| 36 | 4 | `[1]`とそれに続くバイト1から35に対するCRC-32 |

記録は記録のエントリと同じように（印に`0x00`、バイト1から39、最後に印）空きのスロットに書きます。スロットを解放するのは、印への`0x00`の1回のストアです。印はCRCの外にあるので、トリップをクリア済みの記録に変えるのは1バイトです。

### 3.4 呼び出し

サンドボックスの呼び出しの前に、レイヤーはウォッチドッグをリセット（キック）し、有効化のスロットに有効化の記録を書きます。戻りの経路の最初のストアが、超過や故障の後でも、有効化のスロットを解放します（有効化の解除）。呼び出しが戻ったのは、有効化の解除がストアされたときです。どの呼び出しの持ち時間もウォッチドッグの周期よりずっと短いので（lifecycle-events.mdの10節）、呼び出しが有効な状態のウォッチドッグによるリセットは、その呼び出しがロックアップしたことを意味します。起動が`can_arm = false`を報告したレイヤーは、その実行では何も有効にしません。

ヒューズには**ウォッチドッグのフラグ**が要ります。ウォッチドッグによるリセットで立ち、電源投入以外のそれ以降のリセットでも残り、起動が確認したときだけ消えるものです。起動が確認するのは、ストアすべきものをすべてストアしたとき（`complete`）です。マイコンの定義は、マイコンがそのようなフラグを持つかどうかと、その出所を宣言します（`[watchdog] flag`: リセットのフラグがクリアまで残るハードウェアのレジスタか、マイコンの定義のコードが用意するフラグ。例えば、ウォッチドッグによるリセットで立てる保持のレジスタ）。これが無いマイコンにはヒューズがありません。定義の読み込みがヒューズを使えないものとして報告し、レイヤーはロックアップヒューズなしでサンドボックスの呼び出しを動かします。

### 3.5 起動

各レイヤーの起動は、拡張を動かす前に、まず終わったものを解放し（手順3）、判定やトリップの場所を作り、その後で次のことをします。

1. **分類。** 有効化のスロットが有効化されていて、どのセルにも判定が無いほかのセルごとに、自分のセルに判定をストアします。ウォッチドッグのフラグが立っていれば*ロックアップ*、立っていなければ*正常*です。場所が無ければ、`complete`と`can_arm`はfalseです。
2. **自分の呼び出し。** 自分の有効化のスロットが有効化されているとき、判定がロックアップを示すとき、または判定が無くウォッチドッグのフラグが立っているときに、ロックアップしたものとします。ロックアップした呼び出しのidがインストールされていれば、トリップの記録を得て（重複なし）、その後で有効化のスロットを解放します。場所が無ければ、有効化のスロットは有効化のままで、`can_arm`と`complete`はfalseです。ロックアップした呼び出しのidがインストールされていなければ、古いものとして記録して解放します。正常な呼び出しはただ解放します。
3. **自分の記録**（上のとおり、最初に行います）。idがインストールされていないトリップは古いものです。このレイヤーが解放します。ほかのセルにクリアの要求があり、自分のクリア済みが無いトリップは、クリア済みになります（1バイト）。クリアの要求は、ほかのセルがそのクリア済みを持つとき、またはほかのセルがそのトリップを持たないときに解放します。クリア済みは、ほかのセルがその要求を持たないときに解放します。判定は、ほかのセルの有効化のスロットがそのidを持たないときに解放します。
4. **結果。** インストールされているトリップは、その実行で無効にします。ほかのセルに判定があるidは保留します（この実行では有効にしません）。ほかのセルのトリップは報告し、それに基づいて動くことはありません。

そのため、アプリやリレーのロックアップは、ブートローダの起動をそのまま通り抜け（ブートローダは自分のセルに判定をストアするだけです）、アプリの起動がトリップします。ブートローダのロックアップは、ブートローダの次の起動がトリップします。有効化、呼び出し、戻り、有効化の解除のどのバイトでのリセットも、戻った呼び出しをトリップしません。起動中のリセットはフラグと有効化の記録を残すので、次の起動が同じ判断を繰り返します。

### 3.6 クリア

DAGONには、トリップをクリアする要求はありません。プロトコルにもCLIにもありません。形式のモデルが要求について持っているのは次のことです。エージェントは自分のセルのアプリのトリップを解放するか、ブートローダのトリップに対してクリアの要求をストアします。ブートローダの次の起動がトリップをクリア済みに変え、双方は相手のものを見たときに自分の記録を解放します。1つの要求は1つのトリップをクリアします。idがインストールされているトリップをクリアするものは、ほかにありません。

### 3.7 主張の限界

電源投入はウォッチドッグのフラグを消します。分類する前のロックアップは失われますが、偽造はされません。外来のバイトも同じように記録を壊すことがあります。正常の判定が壊れると、その後のウォッチドッグによるリセットが、その中断された呼び出し（戻らなかったもの）をロックアップと分類します。クリア済みの記録が壊れると、残っているクリアの要求が、同じ拡張の次のトリップをもう1度クリアします。セルがいっぱいになると、記録のどれかが解放されるまで、そのレイヤーは何も有効にしません。クリアの要求は無いので（3.6）、idがインストールされているトリップは残ります。

### 3.8 バージョン付け

ヒューズのレイアウトはそれぞれ6つの印の値を持ち、ほかのどのレイアウトの値とも`0x00`とも違います。レイアウト1は`0xA1`から`0xA6`を使い、後のレイアウトはその値をここに挙げます。CRCはレイアウトの番号を初期値にします。別のレイアウトの記録は、この読み手には空きのスロットで、それに基づいて動くことはありません。

## 4. マイコンの識別

`identity(id)`は、`SHA-256("dagon-mcu/" ‖ id)`の最初の8バイトをリトルエンディアンのu64にしたものです。`id`はマイコンの定義の`id`です。識別を持つ場所はどれも、64ビットすべてを持ちます。識別を持つ場所: `image-header`、`identity-reply`、`version-0x06`、`topology-node`（モデルの`identity::CARRIERS`。テストがこの行と照合します）。定義の読み込みは、どれかの場所の幅で識別が一致する2つの定義を、両方のidを示して受け付けず、その場所の幅ですべてゼロかすべて1の識別を受け付けません。読み込んだどの定義とも完全には一致しない識別のデバイスは、不明と表示します。数値のマイコンの表はありません。

## 5. コンパイル済みの構成

### 5.1 本体（`topology-bin` 1）

先頭は16バイトです。マジック`DGTP`、レイアウトu16 LE（1）、ノードの数（1から`MAX_NODES`）、リンクの数（≤ `MAX_LINKS`）、制約の数（≤ `MAX_CONSTRAINTS`）、ゼロ7バイト。続いて次のものです。

- ノードは各40バイト: 番号、役割、ポートの種類、試行の上限、待ち受け時間ms u16 LE、マップのid、順番、復旧の段階[3]、ゼロ5バイト、オフセット16にマイコンの識別u64 LE、オフセット24にターゲットのタグ[16]。
- リンクは各16バイトで、イメージのツールのリンクのレイアウトです。
- 制約は各16バイトで、マニフェストの制約のレイアウトです。

正規の形: ノードの`index`は位置と同じ、リンクは`to`の順、予約のバイトはゼロです。デコーダは符号化し直して比べます。ホストの`host.topology.pushed`と親機の`relay.children_set`は、本体のSHA-256を持ちます。

### 5.2 親機での保存

TOPOLOGYの領域は、同じ大きさで別々に消去できる2つのバンクです。各バンクは64バイトのヘッダで始まります。

| オフセット | 大きさ | 欄 |
|---|---|---|
| 0 | 1 | コミット: `0xC1`（保存のレイアウト1） |
| 1 | 3 | ゼロ |
| 4 | 4 | 連番u32 LE |
| 8 | 4 | 本体の長さu32 LE |
| 12 | 32 | 本体のSHA-256 |
| 44 | 4 | `[1]`とそれに続くバイト1から43に対するCRC-32 |
| 48 | 16 | ゼロ |

バイト1から3と48から63はゼロとして書き込み、読み手は確かめません（バイト1から3はCRCの対象です）。

その後に本体が続きます。バンクが数えられるのは、コミットバイトが`0xC1`で、長さが収まり、CRCが一致し、本体のSHA-256がヘッダのものと同じときです。コピーは、数えられるバンクのうち連番が新しいもの（連番の順）です。数えられるバンクが無ければ、コピーはありません。

**書き込み**（イメージのライフサイクル`written`、ターゲットTOPOLOGY）: ホストはバンクの容量より大きい本体を、1バイトも送る前に拒み、親機も消去の前にもう一度拒みます。それ以外のとき、親機はコピーでないバンク（コピーが無ければバンク0）に、連番 = コピーの連番 + 1（無ければ1）で書きます。バンクを消去し、本体を書き込み、ヘッダのバイト1から63を書き込み、コミットバイトを書き込みます。書き込みのステップを0から、消去または書き込みの1バイトごとに1つ数えると、コミットバイトはステップ`bank size + body
length + 63`です。そのステップが終わる前に止まった書き込みは、前のコピーを1バイトも変えず残します。終わった後は新しいコピーです。その後の読み出しは、次の書き込みまで同じ答えを返します（1）。書き込みが終わると、前のコピーには届かなくなります。遷移は、コピーが無かったときは`Absent → Written`、それ以外は`Written → Written`です。

**読み出し**はリレーの起動時です。本体を解読できないコピー（親機が読まないレイアウトの番号や、不正な形）は無いものとして読み、プロジェクトの予備の一覧を使います（`relay.children_set { source: Fallback }`）。本体は全部適用するか、まったく適用しないかです。

モデルはすべてのシナリオのすべての操作の後でこれらを確かめます。`tests/fixed.rs`の固定のケースは守る性質を名前で示します。

| Id | 性質 |

| P1 | 手元のすべてのエントリを、そのレイアウトのすべてのアプリがリプレイします。 |
| P2 | リプレイするイベントはどれも、読み手のレイアウトの手元の追記です。途中で切れた書き込みは受け付けません。 |

| P5 | 読み手は、新しいブートを古いブートより先に報告しません。順序づけられない組には不確かと印を付けます。順序づけられない組は、開始した段階が異なるか、同じ段階が開始した2つのシーケンスか、同じ段階の2^30以上離れた番号です。 |

## 7. ブートローダの試行のセル

stage0は待機中のブートローダの起動の回数を、フラッシュではなく2つの保持のワードで数えます。こうするとstage0にはフラッシュの書き手がなく（stage0には書き込まないので、持つコードをできるだけ減らします）、書き手の不具合が、何も起動しないstage0に変わることはありません。`dagon_core::bootcore`がコーデックで、そのテストが証明です。

| マイコン | 場所 | 残るもの | 失うもの |
|---|---|---|---|
| RP2040 | ウォッチドッグのSCRATCH0、SCRATCH1（ブートROMはSCRATCH4-7を使います） | 電源投入とRUNピン以外のすべてのリセット | 電源 |
| STM32F401RE | RTCのバックアップレジスタBKP0R、BKP1R | ウォッチドッグのものを含むすべてのシステムリセット | バックアップドメインの電源（VBATを結んでいるところではVDD） |

待機中のイメージ`p`の起動`n`（最大15）の値は、1つのワード`0xB7 << 24 | p.digest16[0] << 16 | p.digest16[1] << 8 | n << 4 | (!n &
0xF)`で、両方の場所にストアします。ワードが`p`について数えられるのは、タグ、ダイジェストのバイト、回数の検査（下位4ビットは回数の補数）が成り立つときだけです。セルは2つのワードの回数の大きいほうを数え、`[0, 0]`はクリアされたセルです。ワードはそれぞれ1回のストアなので、リセットが2つのあいだに来ることがあります。その場合、新しいワード1つと古いワード1つでも新しい起動を数え、少なくなることはありません。ランダムなワードが一致する確率は2^-28で、一致してもstage0がそのコアを早くあきらめるだけです。

実行可能なモデルは`dagon-retained-model`の`world_trial`です。本番のコーデックと、stage0とブートローダのルール（`bootcore::choose`、`settle`）を、2つのワードの上で動かします。新しいコアは良いものか壊れたものとして待機にし（壊れたコアはstage0の検査を通り、自分の検査に失敗します）、セルへのどのストアの後にも（セルの検査のものを含み、マイコンの順に、ワード0、次にワード1）、リセットか電断（セルはクリアかランダムになります）を入れます。シードのシナリオを`cargo test`で実行し、完全なプロファイルではずっと多く実行します。その性質を、すべての操作の後で確かめます。

| Id | 性質 |
|---|---|
| C1 | 2回の電断のあいだに、待機中のコアを試行として起動するのは最大`max`回です。 |
| C2 | それ以上の故障が無ければ、最大`max + 1`回のブートで試行が終わります。待機中のコアは無く、あるコアが動きます。 |
| C3 | 壊れたコアが確定することはありません。 |

マイコンの定義のスイープ（`a_power_cut_at_every_flash_step_leaves_a_bootable_core`）は、フラッシュの側を足します。書き込みのすべてのフラッシュ操作での電断で、状態ログのコンパクションも含みます。

書いたものをまったく保持しないセルは、起動したブートローダとアプリが実行する`bootcore::cell_holds`が見つけます。そのようなノードはブートローダを受け取らず、それに気づいた待機中のコアは自分で元に戻ります。

回数を持つワードがあるセルはstage0が書いたものなので保持しており、検査はその上に何も書きません。何も数えていないセルにだけ、検査用の値（セルのワードが取らない値）と元の値を、ワードごとに書き、それぞれ読み返します。そのため、検査の中でのリセットで、セルの数える起動が少なくなることはありません。

主張の限界: それぞれの場所が、挙げたリセットをまたいで値を保つことは、ベンダーが文書で示している動作です。
