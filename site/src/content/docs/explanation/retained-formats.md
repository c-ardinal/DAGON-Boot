モデルはホスト専用で、リリースしません。各形式のコーデックはモデルのトレイトです（`RecordCodec`、`FuseCodec`、`BodyCodec`）。モデルのコーデックの証明はホスト上で実行します。設計上、ファームウェアのコーデックは同一のトレイトを実装し、同一のハーネスで試験します。

```
cargo test -p dagon-retained-model                       # 10^4 scenarios per world, fixed cases
cargo test -p dagon-retained-model --release -- --ignored # 10^6 scenarios per world
DAGON_MODEL_SCENARIOS=<n> DAGON_MODEL_SEED=<seed>         # override count and base seed
```

失敗したシナリオは、そのシード、構成、そして同一の性質でなお失敗する最小の一覧まで縮小した操作の一覧を表示します。そのケースを回帰テストとして`tests/fixed.rs`に追加します。

## 1. 故障モデル

証明がハードウェアについて仮定する内容と、注入する故障です。

- **ストア。** 保持メモリへの書込は、プログラム順にバイト単位のストアで実施します（1回の書込ステップの間にデータメモリバリアを挟んだvolatileのストア）。幅の広いストアは、異なる2個のステップのバイトを混在させない場合に使用可能です。32ビット単位だけのレジスタファイルは、ステップの隣接バイトを既存の値で再書込します。実行はどのバイトの後にも停止する場合があります（リセットか電断）。モデルは全書込の全バイトの後にこの停止を注入します。
- **リセット**は保持のバイトを残存させます。**電断**は、定義の`[boot.record] survives`の宣言に従います。`reset-random`（バイトはランダム、SRAM）、`reset-cleared`（バイトはゼロ、レジスタ）、`power`（バイトは残存、バッテリバックアップ）です。
- **NORフラッシュ**は`0xFF`に消去し、ビットを1から0に書込します。中断された消去は、先頭の一部を消去済に、残存部分を旧値かランダムな値のままにします。中断された書込は、先頭の一部を書込済にします。どのバイトも（書込が中断されたコミットバイトも同様に）、次回の消去か書込まで、読出のたびに同一の値になります（弱いビットはありません）。一部だけ書込したバイトで異なる値を返却する場合があるフラッシュでは、マイコン定義のコードが、2回の読出の値が一致するまでコミットバイトを再読出する必要があります。
- **外来のバイト。** どのバイトも、その形式の書込側ではないもの（同一段階の別レイアウトの書込側や、故障）に上書きされる場合があります。モデルは全領域にランダムなバイトを注入します。

2個の保証は確率的です。ランダムなバイトが有効なエントリや記録として受理されるのは、8ビットのコミット値とCRC-32が偶然一致した場合だけです（スロットごとに最大2^-40）。新規ブート記録のシーケンスが以前のシーケンスの番号とタグを反復する確率は、エントロピーワードの最小エントロピーがkビットの場合に約2^-kで（2.3）、これが問題になるのは、読込側が前回のリプレイで参照した識別子に対してだけです。以下のその他の保証は例外なく構造的なものです。確率ではなく、どの中断点でも成立します。

## 2. ブート記録（`boot-record` 1）

この文書のバイトの範囲は両端を包含します。「バイト1から23」は、オフセット1、2、…、23の23バイトです。

### 2.1 配置

マイコン定義の`[boot.record]`は、領域（最大`RECORD_MAX` = 4096バイト）、書込側ごとに1個のリング（バイトの範囲、ブート順に列挙）、エントロピーワード（2.3）を宣言します。リング0はDAGONの最初の段階（マイコンにあれば、リセット後に最初に動作する小規模なプログラムであるstage0）のリングで、リング1は後続の段階のリング、以下同様で、書込側は最大16です。リングは`bytes / 28`個のエントリのスロットを保持し、2から256個です。リングは相互に重複せず、領域内にあります。レジスタファイルの予約アドレスは、どのリングの外にもあります。同一の定義が全イメージの`memory.x`に反映されます。

### 2.2 エントリ

28バイト、リトルエンディアンです。

| オフセット | サイズ | 欄 |
|---|---|---|
| 0 | 1 | コミット: `0xB1`はコミット済。その他の値はレイアウト1のエントリではありません |
| 1 | 1 | フラグ: ビット0 `start`（書込側による実行の最初のエントリ）、ビット1 `epoch`（新規シーケンスの最初のエントリ）、ビット2-3はゼロ、ビット4-7 `opener` |
| 2 | 1 | 書込側の`event`の形式番号 |
| 3 | 1 | イベントの種類 |
| 4 | 4 | `eseq`: 書込側の連番 |
| 8 | 4 | `boot`: このブートを開始した段階における最初のエントリの`eseq` |
| 12 | 4 | `boot tag`: ブートを開始した段階のシーケンスのタグ |
| 16 | 4 | `tag`: この書込側のシーケンスのタグ |
| 20 | 3 | ペイロード（イベントの短縮形） |
| 23 | 1 | ゼロ |
| 24 | 4 | `[1, writer index]`と後続のバイト1から23に対するCRC-32（ISO-HDLC） |

エントリが有効なのは、コミットバイトが`0xB1`で、予約のビットとバイトがゼロで、CRCが一致する場合です。CRCはレイアウト番号と書込側番号も計算対象とするので、別レイアウトのエントリや、別の書込側のリングにあるエントリは、決して有効になりません。

**追記**の手順は以下の順です。バイト0に`0x00`をストアします。バイト1から27をストアします。バイト0に`0xB1`をストアします。2回ストアするのはコミットバイトだけで、それも自身の追記内だけです。最初のストアは、他のバイトの変更前にスロットを無効にし、最後のストアは、全バイトの書込後にスロットを有効にします。中断箇所を問わず、中断された書込で失うのは、有効なエントリの上書き中の場合も同様に最大でそのエントリだけで、読込側が受理するものが2回の書込から生成されることはありません。その他の欄を再書込することはありません。

### 2.3 書込側

書込側の番号は**シーケンス**を形成します。シーケンスは空白のリングで開始し、全エントリで1個のタグを共有します。段階は実行ごとに1回書込側をオープンし、**自身のリングだけ**を読込します。

1. 全スロットを1回ずつ解読します（スロットごとにCRC 1回）。最新のエントリは、後方2^24の連番以内に有効なエントリが最多の有効なエントリです（同数なら番号が上位のスロット）。全スロットを使用済のリングでは、一周をまたいで最大の`eseq`になります。
2. **破損のないリング。** リングが破損していないのは、書込側自身の追記だけで生じる状態と完全に同一の場合です。全スロットが有効で、番号が最新のエントリからスロットごとに後方へ減少する場合か、最初の一周の前で、スロット0から*p*（最新のエントリ）までが有効で、スロット0の`epoch`のエントリまで減少し、それ以降のスロットが全部ゼロの場合です。
3. **継続。** 最新のエントリがある場合、次回の追記は後続のスロット（`slots`の剰余）に、そのエントリのタグで実施します。`eseq`は、リングが破損していないなら最新 + 1、破損しているなら最新 + `slots`です（書込側が書込していないバイトがエントリを破損させ、そのエントリがローカルの最新より後のエントリだった可能性があるためです。この番号の飛びで破損したエントリをスキップし、読込側はその飛びをギャップとして提示します）。
4. **新規シーケンス。** 有効なエントリが不在の場合、書込側はリングの全バイトにゼロをストアし、スロット0に`epoch`で追記します。`eseq`は、領域全体の未加工バイトに対するFNV-1a-32で、基底は`0x811C9DC5` XORエントロピーワードです。タグは同一バイトのFNV-1a-32で、基底は`0x050C5D1F` XOR左に16回転したエントロピーワードです。
5. **ブート。** 前段階からの引渡（2.4）が、このレイアウトで有効で、より前の書込側を指定する場合は、その引渡を使用します。それ以外の場合は、この段階が自身でブートを開始します（`opener` = 自身の番号、`boot` = 最初のエントリの`eseq`、`boot tag` = 自身のタグ）。ブートを開始する段階は、引渡に先行して最初のエントリ（`entry`イベント）を追記します。
6. 実行の最初のエントリは`start`を保持します。

書込の位置は定義の定数と、書込側が自身のリングで検証したエントリだけに由来します。そのため、外来のバイトがストアをリング外へ誘導することは不可能です。開始の値を意図的にCRCにしていないのは、CRC-32で保護したエントリの領域に対するCRC-32が、その内容にほとんど依存しないからです。

**エントロピーワード。** マイコン定義はエントロピーワードの出所を宣言します（`[boot.record] entropy`）。領域だけでは以前の状態に回帰する場合があります（`survives = reset-cleared`の電源投入後の全ゼロや、同一段階の別レイアウトの書込側がリングを消去した後）。そのため、このワードは新規シーケンスごとに16ビット以上の最小エントロピーが必要です。この条件を満たす出所はどれでも有効です。ハードウェアの乱数生成器、リングオシレータのランダムなビットの反復サンプル、低速と高速のオシレータによる周期キャプチャ、内部センサをADCで反復変換した値の下位ビットなどです。出所が不在のマイコンには、ブート記録はありません。

**stage0の上限。** 書込側は記録対象の全段階で動作し、stage0も対象です。そのため、書込側の所要時間はその段階の時間上限（stage0では`stage0.max_ms`）に計上します。オープン時にスロットごとのCRC 1回、新規シーケンスでリングの消去、イベントごとに追記1回です。stage0はブートごとに少数のイベントだけを記録します。stage0のリングは2から4スロットで十分です。

### 2.4 引渡

段階はジャンプ時に4個の32ビットのレジスタでブートの識別を次段階に引渡します。保持メモリは決して使用しません（ハングした前回のブートが旧値を残存させないように）。

| ワード | 値 |
|---|---|
| 0 | `0x52424744`（`DGBR`） |
| 1 | `boot` |
| 2 | `boot tag` |
| 3 | ビット0-7 `opener`、ビット8-15記録のレイアウト、ビット16-31はワード0から2とワード3のビット0-15（リトルエンディアン）に対するCRC-32の下位16ビット |

受信する段階がこの引渡を使用するのは、マジック、検査、レイアウトが一致し、`opener`が自身の番号未満の場合だけです。別レイアウトで正規の形式の引渡を受信した段階は、その引渡を無変更で次段階に引渡します（途中に別レイアウトの段階が1個あっても、連鎖が途切れないように）。それ以外の場合は、自身のブートを引渡します。この記録の導入以前の段階は、ブートの開始を次段階に委任します。

### 2.5 読込側

エージェントは起動時に1個のレイアウトで領域を1回読込します（書込はしません）。書込側ごとに、最新から2^24以内の有効なエントリを時系列順に読込します。実行は各`start`のエントリか、ブートの境界で開始します。書込側ごとに**範囲**（`from` = ローカルで最古の`eseq`と、そのエントリが`epoch`を保持するかどうか。保持するなら、このシーケンスにそれ以前のエントリはありません）と、欠落した連番の範囲ごとの**ギャップ**を提示します（番号の飛びの後は、ギャップ内の番号が未使用の場合があります）。有効なエントリが不在の書込側は**エントリなし**と提示します。

ブートは全書込側の実行順を統合して順序付けし、同一段階が開始したブートは番号で順序付けします。

- ブートを開始した段階の使用中のシーケンス（ローカルの最新エントリのタグ）のブートは、その他のどのシーケンスのブートよりも後のものです。
- 使用中のシーケンス内では、ローカルの最新エントリから後方への距離で順序付けします（そのエントリより前方2^24以内のブートは、より後のブートです。そのエントリは破損しています）。
- その他のシーケンス内では、差が2^30未満の場合に連番の順で順序付けします（番号で順序付けするのは、どの書込側の実行順でも関係付け不可能な組だけです）。
- その他の異なる2個のシーケンスのブートや、その他のシーケンスで2^30以上離れたブートは、番号では順序付けしません。

読込側は、後のブートを前のブートより先行して報告することはありません。順序付け不可能な組は、不確実とマークします（両方のブートに`uncertain`）。そのような組は以下のいずれかです。

- どの書込側の順でも関係付け不可能な、別々の段階が開始したブート（2.7）
- ブートを開始した1個の段階の、使用中ではなくなったシーケンスのブート

リプレイ: ブートは時系列順、ブート内では書込側の順、その後にシーケンスの順です。各イベントはそのカタログのイベントとして`replayed: true`と識別子`(writer, tag, eseq)`を付与してリプレイします。ブートは`(opener, boot, boot tag)`です。欠落の報告も同時にリプレイします。`plan`、`commit`、`self_check`、`confirm`はこの記録を読込しません。`app.trial_started`と`app.rolled_back`は状態ログに由来します。

### 2.6 受信側

リプレイは最低1回です。ローカルの全エントリを、起動のたびにリプレイします。あるリプレイになかった識別子が再度リプレイされることはありません。そのため、受信側は`(layout, writer, tag, eseq)`を前回読込したリプレイと比較して重複を除去すれば十分で、それ以前のものを保持する必要はありません。書込側は以前に追記した識別子を再度追記しません（2.3の手順3は破損したエントリをスキップします。新規シーケンスには新規タグがあります）。そのため、2.7の限界内では、新規イベントを受信済のイベントと混同することはありません。`from`が、受信側がその書込側から最後に受信した識別子より後の範囲、ギャップ、`epoch`の開始は、その間のエントリの欠落です。

### 2.7 主張の限界

- **2^32の一周。** 識別子が反復するのは、1個のシーケンスで書込側が2^32回追記した後だけです。1個の書込側の追記で2^32 − `slots`回より離れた2回のリプレイを読込する受信側は、新規エントリと同一番号の旧エントリを区別不可能です。同様に、ブートを開始した段階の追記で2^32 − `slots`回より以前のブートへの、後段階の関連付けは、最近のブートとして配置される場合があります。また、ブートを開始した段階が保持を終了したシーケンスの2個のブートが、その追記で約3·2^30回以上離れていて、どの書込側の実行順でも関係付け不可能な場合は、順序を誤る場合があります（2^32をまたぐ連番の順では、そのような組は逆向きに2^30未満の差と判定されます。2.5）。
- **反復する破損。** 書込側が書込していないバイトが、前回から`slots`個のエントリを追記するまでの間に最新のエントリを再度破損させると、2.3の番号の飛びでは不足し、書込側が破損したエントリの番号を再使用する場合があります（その欠落は提示されません）。最初の一周の間にスロットを全部ゼロにする破損は検出しません。
- **ブートを開始する段階の交代。** 1個の書込側が読込側のレイアウトでの記録を中止し、再開する場合（間に旧版か別レイアウトのstage0がある場合）、その書込側が開始したブートと、次段階が自身で開始したブートは、相互に順序付けされません。読込側はこれを不確実とマークします。順序付けには両方の段階が書込するカウンタが必要で、書込側の独立性がそれを許容しません。
- **分割したブート。** チェーンの途中にこの記録の導入以前の段階がある場合、または1個のブートに2種類の記録レイアウトの段階がある場合は、後段階がブートを再度開始する場合があります。そのブートは2個としてリプレイされます。

### 2.8 VERSION

0x11（ブート記録の要約）: `layout u8, boots u8, flags u8`（ビット0: あるブートが不確実。ビット1: 欠落を提示済、つまりある書込側にギャップか、最古のエントリが`epoch`の開始ではない範囲がある）、その後に最新のブートの`opener u8, boot u32 LE, boot tag u32 LE, count u8`と、そのブートの書込側ごとの最後のエントリを`writer u8, format u8, kind u8,
payload[3]`として返却します。0x12は領域を未加工で返却します。`offset u16`と、最大`RECORD_PAGE(link)`バイトです。ホストがページを連結し、この読込側で解読します。

### 2.9 バージョン管理

レイアウト*n*（1から15）は`0xB0 | n`でコミットし、そのCRCは*n*を初期値にします。16以上のレイアウトは、`0x00`でも以前のどのレイアウトの値でもないコミット値を採用し、ここに列挙します。読込側は、最初のバイトが別レイアウトのコミットであるスロットを計数し（刻みが異なる箇所では近似の数です）、別レイアウトの記録の存在を報告可能ですが、解読はしません。書込側のイベントの符号化は、その書込側の`event`の番号とともに変化し、番号は各エントリにあります。

## 3. ロックアップヒューズ（`boot-record` 1）

### 3.1 セル

サンドボックスの呼出を実行するイメージの種類ごとに、セルが1個あります。ブートローダのセルとアプリのセルです（アプリとリレーのレイヤーは共有します。コアごとに、オープン中のサンドボックスの呼出は最大1個です）。セルは有効化のスロットと後続の記録のスロットで構成します（`[boot.record] fuse`が、記録の隣に両方のセルとそのスロット数を宣言します）。セルにストアするのは、そのセル自身のレイヤーだけです。どのレイヤーの起動も、全セルを読込します。

### 3.2 ヒューズのid

`SHA-256("dagon-fuse/1" ‖ layer u8 ‖ slot u32 LE ‖ image header digest
[32] ‖ chain index u32 LE ‖ artifact SHA-256 [32])`。欄の幅は固定なので、異なる2個の呼出箇所が同一の入力になることはありません。スロットや拡張の数に上限はありません。拡張の新規ビルドや新規イメージは、新規idです。

### 3.3 記録

40バイトです。

| オフセット | サイズ | 欄 |
|---|---|---|
| 0 | 1 | マーク: `0xA1`有効化、`0xA2`トリップ、`0xA3`クリアの要求、`0xA4`ロックアップの判定、`0xA5`正常の判定、`0xA6`クリア済。その他の値は未使用 |
| 1 | 1 | レイヤー |
| 2 | 2 | ゼロ |
| 4 | 32 | ヒューズのid |
| 36 | 4 | `[1]`と後続のバイト1から35に対するCRC-32 |

記録は記録のエントリと同様に（マークに`0x00`、バイト1から39、最後にマーク）未使用のスロットに書込します。スロットを解放するのは、マークへの`0x00`の1回のストアです。マークはCRCの対象外なので、トリップをクリア済の記録に変更するのは1バイトです。

### 3.4 呼出

サンドボックスの呼出に先行して、レイヤーはウォッチドッグをリセット（キック）し、有効化のスロットに有効化の記録を書込します。復帰経路の最初のストアが、超過や故障の後も、有効化のスロットを解放します（有効化の解除）。呼出の復帰は、有効化の解除をストアした時点です。どの呼出の割当時間もウォッチドッグの周期より大幅に短時間なので（lifecycle-events.mdの10節）、呼出が有効な状態でのウォッチドッグによるリセットは、その呼出がロックアップしたことを意味します。起動が`can_arm = false`を報告したレイヤーは、その実行では何も有効化しません。

ヒューズには**ウォッチドッグのフラグ**が必要です。ウォッチドッグによるリセットでセットされ、電源投入以外の以降のリセットでも残存し、起動の確認時だけクリアされるフラグです。起動が確認するのは、ストア対象を全部ストアした時点（`complete`）です。マイコン定義は、マイコンがそのようなフラグを保持するかどうかと、その出所を宣言します（`[watchdog] flag`: リセットのフラグがクリアまで残存するハードウェアのレジスタか、マイコン定義のコードが用意するフラグ。例えば、ウォッチドッグによるリセットでセットする保持のレジスタ）。このフラグが不在のマイコンにはヒューズがありません。定義の読込がヒューズを使用不可能と報告し、レイヤーはロックアップヒューズなしでサンドボックスの呼出を実行します。

### 3.5 起動

各レイヤーの起動は、拡張の実行前に、最初に終了済のものを解放し（手順3）、判定やトリップの格納先を確保し、その後に以下の処理を実行します。

1. **分類。** 有効化のスロットが有効化済で、どのセルにも判定がない他のセルごとに、自身のセルに判定をストアします。ウォッチドッグのフラグがセット済なら*ロックアップ*、未セットなら*正常*です。格納先がなければ、`complete`と`can_arm`はfalseです。
2. **自身の呼出。** 自身の有効化のスロットが有効化済の場合、判定がロックアップの場合、または判定がなくウォッチドッグのフラグがセット済の場合に、ロックアップしたと判断します。ロックアップした呼出のidがインストール済なら、トリップの記録を取得して（重複なし）、その後に有効化のスロットを解放します。格納先がなければ、有効化のスロットは有効化のままで、`can_arm`と`complete`はfalseです。ロックアップした呼出のidが未インストールなら、失効済として記録して解放します。正常な呼出は単に解放します。
3. **自身の記録**（前述のとおり、最初に実施します）。idが未インストールのトリップは失効済です。このレイヤーが解放します。他のセルにクリアの要求があり、自身のクリア済がないトリップは、クリア済になります（1バイト）。クリアの要求は、他のセルがそのクリア済を保持する場合、または他のセルがそのトリップを保持しない場合に解放します。クリア済は、他のセルがその要求を保持しない場合に解放します。判定は、他のセルにある有効化のスロットがそのidを保持しない場合に解放します。
4. **結果。** インストール済のトリップは、その実行で無効にします。他のセルに判定があるidは保留します（この実行では有効化しません）。他のセルのトリップは報告するだけで、そのトリップを根拠とする動作はしません。

そのため、アプリやリレーのロックアップは、ブートローダの起動を無変更で通過し（ブートローダは自身のセルに判定をストアするだけです）、アプリの起動がトリップします。ブートローダのロックアップは、ブートローダの次回起動がトリップします。有効化、呼出、復帰、有効化の解除のどのバイトでのリセットも、復帰済の呼出をトリップしません。起動中のリセットはフラグと有効化の記録を残存させるので、次回起動が同一の判断を反復します。

### 3.6 クリア

DAGONには、トリップをクリアする要求はありません。プロトコルにもCLIにもありません。形式のモデルが要求について規定する内容は以下のとおりです。エージェントは自身のセルにあるアプリのトリップを解放するか、ブートローダのトリップに対してクリアの要求をストアします。ブートローダの次回起動がトリップをクリア済に変更し、双方は相手側の記録の検出時に自身の記録を解放します。1個の要求は1個のトリップをクリアします。idがインストール済のトリップをクリアする手段は、他にありません。

### 3.7 主張の限界

電源投入はウォッチドッグのフラグを消去します。分類前のロックアップは失われますが、偽造はされません。外来のバイトも同様に記録を破損させる場合があります。正常の判定が破損すると、以降のウォッチドッグによるリセットが、その中断された呼出（未復帰の呼出）をロックアップと分類します。クリア済の記録が破損すると、残存するクリアの要求が、同一拡張の次回トリップを再度クリアします。セルが満杯になると、いずれかの記録の解放まで、そのレイヤーは何も有効化しません。クリアの要求は存在しないので（3.6）、idがインストール済のトリップは残存します。

### 3.8 バージョン管理

ヒューズのレイアウトはそれぞれ6個のマーク値を保持し、その他のどのレイアウトの値とも`0x00`とも異なります。レイアウト1は`0xA1`から`0xA6`を使用し、後続のレイアウトはその値をここに列挙します。CRCはレイアウトの番号を初期値にします。別レイアウトの記録は、この読込側には未使用のスロットで、その記録を根拠とする動作はしません。

## 4. マイコンの識別

`identity(id)`は、`SHA-256("dagon-mcu/" ‖ id)`の最初の8バイトをリトルエンディアンのu64にした値です。`id`はマイコン定義の`id`です。識別を保持する箇所は、いずれも64ビット全部を保持します。識別を保持する箇所は`image-header`、`identity-reply`、`version-0x06`、`topology-node`です（モデルの`identity::CARRIERS`です。テストがこの行と照合します）。定義の読込は、いずれかの箇所の幅で識別が一致する2個の定義を、両方のidを提示して拒否し、その箇所の幅で全ビットがゼロか全ビットが1の識別を拒否します。読込したどの定義とも完全には一致しない識別のデバイスは、不明と表示します。数値のマイコンの表はありません。

## 5. コンパイル済の構成

### 5.1 本体（`topology-bin` 2）

先頭は16バイトです。マジック`DGTP`、レイアウトu16 LE（2）、ノード数（1から`MAX_NODES`）、リンク数（≤ `MAX_LINKS`）、制約数（≤ `MAX_CONSTRAINTS`）、ゼロ7バイトです。その後に以下の要素があります。

- ノードは各40バイト: 番号、役割、ポートの種類、試行の上限、待受時間ms u16 LE、マップのid、順番、復旧の段階[3]、ゼロ5バイト、オフセット16にマイコンの識別u64 LE、オフセット24にターゲットのタグ[16]。
- リンクは各20バイトで、イメージツールにおけるリンクのレイアウトです。向きはなく、2個の端それぞれにノード、ポートの番号、アドレスがあります。
- 制約は各16バイトで、マニフェストの制約のレイアウトです。

正規の形式: ノードの`index`は位置と同一、リンクの端はノードの順、リンクは端のノードの順、予約のバイトはゼロです。レイアウト1（16バイトのリンク）は読込しません。デコーダは再符号化して比較します。

## 7. ブートローダの試行のセル

stage0は待機中のブートローダの起動回数を、フラッシュではなく2個の保持のワードで計数します。この方式ではstage0にフラッシュの書込側がなく（stage0には書込しないので、保持するコードを最小限にします）、書込側の不具合が原因でstage0が何も起動しない状態になることはありません。`dagon_core::bootcore`がコーデックで、そのテストが証明です。

| マイコン | 位置 | 残存する対象 | 消失する対象 |
|---|---|---|---|
| RP2040 | ウォッチドッグのSCRATCH0、SCRATCH1（ブートROMはSCRATCH4-7を使用します） | 電源投入とRUNピン以外の全リセット | 電源 |
| STM32F401RE | RTCのバックアップレジスタBKP0R、BKP1R | ウォッチドッグによるリセットも対象とする全システムリセット | バックアップドメインの電源（VBATを接続している構成ではVDD） |

待機中のイメージ`p`の起動`n`（最大15）の値は、1個のワード`0xB7 << 24 | p.digest16[0] << 16 | p.digest16[1] << 8 | n << 4 | (!n &
0xF)`で、両方の位置にストアします。ワードが`p`の計数対象になるのは、タグ、ダイジェストのバイト、回数の検査（下位4ビットは回数の補数）が成立する場合だけです。セルは2個のワードのうち回数の最大値を計数し、`[0, 0]`はクリアされたセルです。ワードはそれぞれ1回のストアなので、リセットが2個のストアの間に発生する場合があります。その場合、新規ワード1個と旧ワード1個でも新規の起動を計数し、計数が減少することはありません。ランダムなワードが一致する確率は2^-28で、一致してもstage0がそのコアを早期に断念するだけです。

実行可能なモデルは`dagon-retained-model`の`world_trial`です。本番のコーデックと、stage0とブートローダの規則（`bootcore::choose`、`settle`）を、2個のワード上で実行します。新規コアを正常か破損として待機状態にし（破損したコアはstage0の検査に合格し、自身の検査に失敗します）、セルへのどのストアの後にも（セルの検査のストアも対象で、マイコンの順に、ワード0、次にワード1）、リセットか電断（セルはクリアかランダムになります）を挿入します。シードのシナリオを`cargo test`で実行し、完全なプロファイルではシナリオ数を大幅に増加して実行します。その性質を、全操作の後に確認します。

| Id | 性質 |
|---|---|
| C1 | 2回の電断の間に、待機中のコアを試行として起動するのは最大`max`回です。 |
| C2 | 追加の故障がなければ、最大`max + 1`回のブートで試行が終了します。待機中のコアはなく、あるコアが動作します。 |
| C3 | 破損したコアが確定することはありません。 |

マイコン定義のスイープ（`a_power_cut_at_every_flash_step_leaves_a_bootable_core`）は、フラッシュ側を追加します。書込の全フラッシュ操作での電断で、状態ログのコンパクションも対象です。

書込した値を一切保持しないセルは、起動したブートローダとアプリが実行する`bootcore::cell_holds`が検出します。そのようなノードはブートローダを受信せず、その状態を検出した待機中のコアは自身でロールバックします。

回数を保持するワードがあるセルは、stage0が書込したセルなので保持が成立しており、検査はそのセルに何も書込しません。何も計数していないセルにだけ、検査用の値（セルのワードが使用しない値）と検査前の値を、ワードごとに書込し、それぞれ再読出します。そのため、検査中のリセットで、セルが計数する起動が減少することはありません。

主張の限界: 各位置が、列挙したリセットをまたいで値を維持することは、ベンダーが文書で明示している動作です。

## 8. 状態ログのキー付記録とリンク診断（`state-log` 1）

状態ログは、イメージのスロットの記録と、ノードが相手について保持するリンク診断を収容します。リンク診断はキー付記録です。この節は、キー付記録、リンク診断の5種類の記録、その追記の規則の規範です。モデルは`dagon-retained-model`の`journal`、`diag`、`world_diag`です。面、面ヘッダ、スロットの記録の畳込は`dagon_format::statelog`と`dagon_core::log`の定義であり、モデルはスロットの記録に対する全操作を、同一のバイト列から開始した`dagon_core::log::Log`と照合します。

各規則は区分を明示します。[ISO]はISO 14229-1に準拠、[AUTOSAR]はAUTOSAR Demに準拠、[DAGON]はDAGONの規則です。

### 8.1 面と記録

[DAGON]ログは交互に使用する2面です。面は32バイトの面ヘッダと、後続の32バイトの記録で構成し、消去済のバイトは`0xFF`です。有効な面のうち世代が最大の面が使用中の面です。記録は順番に畳込し、畳込は最初の消去済記録か、最初のCRC不一致記録で終了します。

| オフセット | サイズ | 欄 |
|---|---|---|
| 0 | 1 | 種別: `0x01`から`0x7F`はスロットの記録、`0x80`から`0xFE`はキー付記録、`0xFF`は消去済 |
| 1 | 3 | 種別ごとの欄 |
| 4 | 4 | `seq`: 連番、リトルエンディアン。畳込は連番を使用しません |
| 8 | 20 | 種別ごとの欄 |
| 28 | 4 | バイト0から27のCRC-32（ISO-HDLC） |

[DAGON]記録は、使用中の面にある最初の消去済記録へ、その32バイト全部の消去を確認した後に追記します。面が満杯の場合、面の末尾がCRC不一致記録の場合、この確認が不成立の場合、追記は事前にコンパクションを実行します。コンパクションは他方の面を消去し、畳込結果を複写し、世代に1を加算した面ヘッダを最後に記録します。その面ヘッダが完成するまで、旧面が有効です。読出側は、未知の種別の記録を無視します。

### 8.2 キー付記録

| オフセット | サイズ | 欄 |
|---|---|---|
| 0 | 1 | 種別: ビット7は1。ビット6は設定記録で0、削除記録で1。ビット0から5はクラス（0から62） |
| 1 | 1 | `n`: 設定記録ではキー長、削除記録では指定するキー接頭部のバイト数（0から20） |
| 2 | 1 | 削除記録では対象の最終クラス（自身のクラスから62）。設定記録ではゼロ |
| 3 | 1 | ゼロ |
| 4 | 4 | `seq` |
| 8 | 20 | 設定記録ではキー（`n`バイト）、その後に値。削除記録ではキー接頭部（`n`バイト）、その後にゼロ |
| 28 | 4 | CRC-32 |

[DAGON]畳込は、クラスの意味に関する知識を必要としません。

- 設定記録のキーは、クラスと`n`バイトのキー欄の組です。同一キーの最新の設定記録がそのキーの値であり、同一キーの以前の設定記録を削除します。
- 削除記録は、クラスが削除記録のクラスから最終クラスまでの範囲にあり、キーが削除記録のキー接頭部で開始する、以前の設定記録を全部削除します。`n`が0の削除記録は、対象クラスの全キーを削除します。削除記録自体は畳込結果に残存しません。
- 種別が`0x80`から`0xFE`で、表に違反する記録（20を超過する`n`、自身のクラス未満か62を超過する最終クラス、ゼロ以外の予約バイト）はキー付記録ではありません。畳込はこの記録を無視し、コンパクションは複写しません。

[DAGON]コンパクションはスロットの記録を従来どおり記録し、その後に、面の後続記録が削除しない設定記録を全部、ログの順番で、バイト単位で同一のまま（連番とCRCも同一）複写します。削除記録と削除済の設定記録は複写しません。コンパクションは面を記録単位で参照し、表を保持しません。そのため、クラスを認識しないコードも全クラスを複写します。ブートローダは、自身よりバージョンが後のアプリが追記した記録を複写します。他方の面が全記録を収容不能の場合、コンパクションは失敗し、旧面が有効です。

| クラス | 記録 |
|---|---|
| 0 | 通信実績 |
| 1 | DTC状態 |
| 2 | シードカウンタ |

### 8.3 リンク診断の記録

[DAGON]相手は、ノードがその相手に到達するリンクの`link`と`addr`です。記録は以下の5種類です。

| 記録 | 種別 | `n` | バイト8から27 |
|---|---|---|---|
| 通信実績 | `0x80` | 2 | `link`、`addr`、個体識別子（16）、ゼロ（2） |
| DTC状態 | `0x81` | 5 | `link`、`addr`、DTC番号（3、上位バイトが先頭）、状態、エージ、不合格サイクル数、ゼロ（12） |
| シードカウンタ | `0x82` | 0 | カウンタ（u32、リトルエンディアン）、ゼロ（16） |
| DTCクリア | `0xC1` | 5、2、0のいずれか | `link`、`addr`、DTC番号（3）。または`link`、`addr`。またはなし。残余はゼロ。バイト2は1 |
| 通信実績クリア | `0xC0` | 2か0 | `link`、`addr`。またはなし。残余はゼロ。バイト2は1 |

- [DAGON]個体識別子は全記録で16バイトです。16個のゼロバイトは識別子の不在を意味します。識別子の供給手段はこの形式の範囲外です。供給手段を保有しない書込側は16個のゼロバイトを記録し、供給手段は16個のゼロバイトを値として生成しません。
- [ISO]状態はstatusOfDTCのバイトです。記録が保持する範囲はビット1から6のみで、記録のビット0とビット7はゼロです。ビット0はRAMに存在し、ビット7は常時0です。
- [DAGON]`0x000001`から`0xFFFFFE`のDTC番号が故障を指定します。`0x000000`と`0xFFFFFF`は記録しません。
- [DAGON]エージは、DTCの確定以降の合格サイクル数です。不合格サイクル数は、連続した不合格サイクルの数です。両方とも1バイトで、255で停止します。
- [DAGON]DTCクリアは、`n`が5の場合に相手1件のDTC1件、`n`が2の場合に相手1件の全DTC、`n`が0の場合に全DTCを消去します。対象はクラス1のみであり、通信実績の記録を削除しません。
- [DAGON]通信実績クリアは、`n`が2の場合に相手1件、`n`が0の場合に全相手を消去します。対象はクラス0から1であり、該当する相手のDTC状態も同時に削除します。
- [DAGON]クラス2を対象とするクリアは存在しません。シードカウンタは全部のクリアの後も残存します。
- [DAGON]クラス0、1、2で上記以外の形の記録（別の`n`、故障を指定しないDTC番号、1から6以外の状態ビット、ゼロ以外の予約バイト）は、未知の形式の記録です。保存側はこの記録を使用せず、コンパクションは複写します。

`link`が255、`addr`が255の相手に対する、連番1の各記録のバイト列です（DTC番号`0xFFFFFE`、状態`0x7E`、エージ255、不合格サイクル数255、カウンタ4294967295）。

### 8.4 DTC状態の遷移

[ISO]記録が存在しないDTCは、状態`0x50`、エージ0、不合格サイクル数0です。これはクリア直後の状態です。

[AUTOSAR]DTCの故障検出カウンタ（FDC）はRAMに存在し、各オペレーションサイクルを0で開始します。不合格標本はFDCの加算幅を加算し、上限は+127です。FDCの+127が検査の不合格です。[DAGON]合格標本はFDCを即時に-128へ設定します。

| 事象 | 記録の変化 | 区分 |
|---|---|---|
| 合格標本 | ビット4が0。ビット2かビット3が1の場合、ビット6が0 | [ISO]ビット4、[DAGON]ビット6 |
| 検査の不合格、ビット1が0 | ビット1、2、5が1。ビット4と6が0。不合格サイクル数に1を加算。不合格サイクル数が確定閾値に到達した場合、ビット3が1。エージが0 | [AUTOSAR] |
| 検査の不合格、ビット1が1 | なし | [AUTOSAR] |
| サイクル終了評価、ビット6が1 | なし | [DAGON] |
| サイクル終了評価、ビット6が0かつビット1が1 | ビット1が0、ビット6が1 | [AUTOSAR] |
| サイクル終了評価、ビット6が0かつビット1が0 | ビット2が0。不合格サイクル数が0。ビット3が1の場合はエージに1を加算し、エージ閾値に到達したエージはビット3とエージを0へ変更。ビット6が1 | [AUTOSAR] |

- [DAGON]オペレーションサイクルは、ノードのアプリ1回の実行（リセットから次回のリセットまで）です。電断は記録の機会なしでサイクルを終了します。そのため、終了したサイクルは、アプリの次回の開始時に、最初の標本に先行して、記録のビット1とビット6から評価します。
- [DAGON]評価結果のビット6は1であり、評価はビット6が1の記録を変更しません。そのため、任意の時点で中断した評価の再実行は、1回の実行と同一の結果に到達します。
- [DAGON]pendingでもconfirmedでもないDTCの合格標本は、記録のビット6を1のまま維持します。評価がそのDTCについて判定する事項が存在しないためです。故障のない相手は、サイクル内で記録を追記しません。実行中のサイクルのビット6は、ビット0と同様にRAMから参照します。
- [AUTOSAR]同一サイクル内で合格標本より後に発生した検査不合格は、エージを0へ変更します。不合格がそのサイクルのエージングを取消します。

### 8.5 追記

[DAGON]全部の変化は追記1件です。記録の欄を2回記録することはなく、記録はCRCまでの32バイト全部が完成した時点で有効です。

- 畳込結果が通信実績の記録を保持しない相手の合格標本は、最初にその記録を追記します。初回に限定しません。電断で中断した記録は、次回の合格標本が再度追記します。畳込結果が`diag_peers`件の相手を保持する場合、新規の相手は記録せず、保存側は満杯を通知します。
- 合格標本と検査の不合格は、その後に、8.4の表が変更する場合にDTC状態を追記します。
- 通信実績の記録がない相手のタイムアウトは標本ではありません。
- クリアは削除記録1件を追記します。畳込結果に該当する記録がないクリアは追記しません。
- シードカウンタは、記録がない状態で0から開始します。要求はカウンタに1を加算した値を追記し、追記の完了後にのみその値を返却します。4294967295では値を返却しません。カウンタは一周しません。
- サイクル終了評価は、変更するDTCごとにDTC状態1件を追記します。

### 8.6 性質

モデルは3種類の故障を注入します。全操作（標本、クリア、シードカウンタの追記、サイクル終了評価、アプリとブートローダのコンパクション）における書込と消去の各バイト後の電断、フラッシュ内の任意位置への外来バイト、復号対象外クラスのキー付記録です。全操作の後に、畳込結果が期待どおりであること、電断後の畳込結果が追記中の記録の直前か直後の状態であること、下表の性質を検査します。下表の性質は電断に対する主張です（外来バイトに対する主張は8.7）。

| Id | 性質 |
|---|---|
| L1 | 通信実績ありと参照される相手は、最後の通信実績クリア以降に合格標本が存在し、参照される識別子はその標本の識別子です。 |
| L2 | 追記が完了した通信実績の記録は、以降の任意の電断、アプリとブートローダのコンパクション、DTCクリアの後も参照されます。 |
| L3 | 完了したクリアの削除対象は、その相手の新規の標本まで、再度参照されません。 |
| L4 | 1サイクルに追記するリンク診断の記録は、最大で、`diag_peers`の3倍、クリア数、シード要求数、クリア対象の相手数の3倍を合計した件数です。相手1件は1サイクルに最大3件（評価か通信実績の記録、最初の合格、最初の不合格）を追記します。クリアは、対象の相手ごとに3件を追加で許容します。 |
| L5 | 全部の書込は2面の範囲内です。 |
| L6 | スロットの記録の畳込結果は、同一のバイト列に対する`dagon_core::log::Log`の畳込結果と一致します。スロットの記録に対する操作は、キー付記録と連番を除外して、`Log`と同一の記録を生成します。キー付記録の追記は、コンパクション経由でのみその畳込結果を変更します。コンパクション後の面は畳込結果の全記録を収容し、収容不能の場合は旧面が有効です。 |
| L7 | サイクル終了評価は、任意の時点で中断した後に再実行すると、1回の実行と同一の結果に到達します。 |
| L8 | pendingDTC、confirmedDTC、エージ、不合格サイクル数は、8.4のとおりにサイクルの結果へ追従します。同一サイクル内で合格より後に発生した不合格も対象です。 |
| L9 | 返却済のシードカウンタの値は、任意の電断の後も、再度返却されません。 |

### 8.7 主張の限界

- **外来バイト。** L1からL9は電断に対する主張です。記録上の外来バイトは畳込をその記録で終了させ、使用中の面ヘッダ上の外来バイトは旧面を有効にします。その場合、ログの内容は過去のある時点の内容か、その一部です。削除記録が削除した設定記録が再度参照され、シードカウンタは過去の値に復帰します。外来バイトに対して成立する主張は、以下の弱い主張のみです。合格標本が一度も存在しない相手が通信実績ありと参照されることはなく（CRC-32の偶然の一致を除外）、L5が成立し、参照される畳込結果を起点に、次回の完了した記録以降でL1からL9が再度成立します。
- **畳込結果で満杯の面。** 畳込結果の記録が面を充足する場合、コンパクションは空きを生成しません。全追記が失敗し、各追記は事前に面を消去します。マイコン定義の`diag_peers`が、畳込結果の記録を1面未満に維持します。
- **中断した記録とブート経路。** 電断で中断した記録は、次回のコンパクションまで、その面を終端にします。ブート経路は消去しないため、その面には追記しません。実行中のアプリの追記がコンパクションを実行するまで、試行は開始しません。
- **両面の消去。** 2面を消去したログは記録を保持しません。全相手が通信実績なしと参照され、シードカウンタは再度0から開始します。

### 8.8 バージョン管理

キー付記録は`state-log` 1に所属します。形式1の全読出側は、種別`0x80`から`0xFE`を8.2のとおりに畳込し、コンパクションで複写します。新規の記録は、未使用のクラス番号を取得します。読出側の変更は不要です。配置を変更する記録は、新規のクラスを取得します。8.1か8.2の表の変更は、新規の`state-log`番号を取得します。
