この文書は、[lifecycle-events.md の 5.5 節](/explanation/lifecycle-events/)が実行可能なモデルに任せている形式の、規範となる仕様です。対象は、ブート記録、ロックアップヒューズ、マイコンの識別、コンパイル済みの構成のノードのレイアウトと置き換えです。ここにある形はどれも `crates/dagon-retained-model` が証明しているものです。形を変えるときは、まずモデルを変え、モデルのテストで決めます。

モデルはホスト専用で、リリースしません。各形式のコーデックはモデルのトレイトです（`RecordCodec`、`FuseCodec`、`BodyCodec`）。本番のコーデックは同じトレイトを実装し、同じハーネスで動きます。そのため、配布するコーデックと証明がずれることはありません。

```
cargo test -p dagon-retained-model                       # 10^4 scenarios per world, fixed cases
cargo test -p dagon-retained-model --release -- --ignored # 10^6 scenarios per world
DAGON_MODEL_SCENARIOS=<n> DAGON_MODEL_SEED=<seed>         # override count and base seed
```

失敗したシナリオは、そのシード、構成、そして同じ性質でなお失敗する最小の一覧まで縮めた操作の一覧を表示します。そのケースを回帰テストとして `tests/fixed.rs` に足します。

## 1. 故障モデル

証明がハードウェアについて仮定することと、注入するものです。

- **ストア。** 保持メモリは、プログラムの順にバイトのストアで書かれます（1 回の書き込みのステップのあいだにデータメモリバリアを挟んだ volatile のストア）。幅の広いストアは、異なる 2 つのステップのバイトを合わせないときに使えます。32 ビット単位だけのレジスタファイルは、ステップの隣のバイトをいまの値で書き直します。実行はどのバイトの後でも止まることがあります（リセットか電断）。モデルは、すべての書き込みのすべてのバイトの後にこの停止を注入します。
- **リセット**は保持のバイトを残します。**電断**は、定義の `[boot.record] survives` が宣言するとおりです。`reset-random`（バイトはランダム、SRAM）、`reset-cleared`（バイトはゼロ、レジスタ）、`power`（バイトは残る、バッテリバックアップ）です。
- **NOR フラッシュ**は `0xFF` に消去し、ビットを 1 から 0 に書き込みます。中断された消去は、先頭の一部を消去済みに、残りを古いかランダムなままにします。中断された書き込みは、先頭の一部を書き込み済みにします。どのバイトも、書き込みが中断されたコミットバイトを含め、次の消去か書き込みまで、読むたびに同じ値になります（弱いビットはありません）。一部だけ書かれたバイトで違う値を返すことがあるフラッシュでは、マイコンのパッケージが、2 回の読み出しが一致するまでコミットバイトを読み返す必要があります。
- **外来のバイト。** どのバイトも、その形式の書き手ではないもの（同じ段階の別のレイアウトの書き手や、故障）に上書きされることがあります。モデルは、すべての領域にランダムなバイトを注入します。

2 つの保証は確率的です。ランダムなバイトが有効な項目や記録として受け付けられるのは、8 ビットのコミット値と CRC-32 の偶然の一致のときだけです（スロットごとに最大 2^-40）。構成の保存は、さらに SHA-256 の一致も求めます。新しいブート記録の並びが以前の並びの番号とタグを繰り返す確率は、エントロピーワードの最小エントロピーが k ビットのとき約 2^-k で（2.3）、これが問題になるのは、読み手が前回のリプレイで見た識別子に対してだけです。下のほかの保証はどれも構造的なものです。確率ではなく、どの中断点でも成り立ちます。

## 2. ブート記録（`boot-record` 1）

この文書のバイトの範囲は両端を含みます。「バイト 1 から 23」は、オフセット 1、2、…、23 の 23 バイトです。

### 2.1 配置

マイコンの定義の `[boot.record]` は、領域（最大 `RECORD_MAX` = 4096 バイト）、書き手ごとに 1 つのリングをバイトの範囲としてブートの順に、そしてエントロピーワード（2.3）を宣言します。リング 0 は DAGON の最初の段階（マイコンにあれば stage0）のもので、リング 1 は次の段階のもの、以下同じで、書き手は最大 16 です。リングは `bytes / 28` 個の項目のスロットを持ち、2 から 256 個です。リングは重ならず、領域の中にあります。レジスタファイルの予約アドレスは、どのリングの外にもあります。同じ定義が、すべてのイメージの `memory.x` に届きます。

### 2.2 項目

28 バイト、リトルエンディアンです。

| オフセット | 大きさ | 欄 |
|---|---|---|
| 0 | 1 | コミット: `0xB1` はコミット済み。ほかの値はレイアウト 1 の項目ではありません |
| 1 | 1 | フラグ: ビット 0 `start`（書き手の実行の最初の項目）、ビット 1 `epoch`（新しい並びの最初の項目）、ビット 2-3 はゼロ、ビット 4-7 `opener` |
| 2 | 1 | 書き手の `event` の形式番号 |
| 3 | 1 | イベントの種類 |
| 4 | 4 | `eseq`: 書き手の連番 |
| 8 | 4 | `boot`: このブートでの開始者の最初の項目の `eseq` |
| 12 | 4 | `boot tag`: 開始者の並びのタグ |
| 16 | 4 | `tag`: この書き手の並びのタグ |
| 20 | 3 | ペイロード（イベントの短い形） |
| 23 | 1 | ゼロ |
| 24 | 4 | `[1, writer index]` とそれに続くバイト 1 から 23 に対する CRC-32（ISO-HDLC） |

項目が有効なのは、コミットバイトが `0xB1` で、予約のビットとバイトがゼロで、CRC が一致するときです。CRC はレイアウトの番号と書き手の番号を束ねるので、別のレイアウトの項目や、別の書き手のリングにある項目は、決して有効になりません。

**追記**は、この順です。バイト 0 に `0x00` をストアする。バイト 1 から 27 をストアする。バイト 0 に `0xB1` をストアする。2 度ストアするのはコミットバイトだけで、それも自分の追記の中だけです。最初のストアは、ほかのバイトが変わる前にスロットを無効にし、最後のストアは、すべてのバイトがそろった後でスロットを有効にします。どこで中断された書き込みでも、有効な項目を上書きしている場合を含め、失うのは最大でその項目だけで、読み手が受け付けるものが 2 回の書き込みから作られることはありません。ほかの欄を書き直すことはありません。

### 2.3 書き手

書き手の番号は**並び**を作ります。並びは空のリングで始まり、すべての項目に 1 つのタグを持ちます。段階は、実行ごとに 1 度書き手を開き、**自分のリングだけ**を読みます。

1. すべてのスロットを 1 度ずつ解読します（スロットごとに CRC 1 回）。いちばん新しい項目は、後ろ 2^24 の連番以内に有効な項目がいちばん多い有効な項目です（同数なら上のスロット）。書き手が埋めたリングでは、一周をまたいで最大の `eseq` になります。
2. **無傷のリング。** リングが無傷なのは、書き手自身の追記が残すものとぴったり同じときです。すべてのスロットが有効で、番号がいちばん新しいものからスロットごとに後ろへ下がるか、最初の一周の前で、スロット 0 から *p*（いちばん新しいもの）までが有効で、スロット 0 の `epoch` の項目まで下がり、それより後のスロットがすべてゼロのときです。
3. **続ける。** いちばん新しい項目があるとき、次の追記は次のスロット（`slots` の剰余）に、その項目のタグで行います。`eseq` は、リングが無傷なら最新 + 1、無傷でなければ最新 + `slots` です（書き手が書いていないバイトが項目を壊していて、それが手元の最新より新しかった可能性があるためです。この飛びで壊れた項目を越え、読み手はそれをギャップとして示します）。
4. **新しい並び。** 有効な項目が無いとき、書き手はリングのすべてのバイトにゼロをストアし、スロット 0 に `epoch` で追記します。`eseq` は、領域全体の生のバイトの FNV-1a-32 で、基底は `0x811C9DC5` XOR エントロピーワードです。タグは、同じバイトの FNV-1a-32 で、基底は `0x050C5D1F` XOR 左に 16 回転したエントロピーワードです。
5. **ブート。** 前の段階からの引き渡し（2.4）が、このレイアウトで有効で、より前の書き手を示すときは、それを使います。それ以外のときは、この段階が自分でブートを開始します（`opener` = 自分の番号、`boot` = 最初の項目の `eseq`、`boot tag` = 自分のタグ）。ブートを開始する段階は、引き渡す前に最初の項目（`entry` イベント）を追記します。
6. 実行の最初の項目は `start` を持ちます。

書き込みの位置は、定義の定数と、書き手が自分のリングで検証した項目からしか来ません。そのため、外来のバイトがストアをリングの外に向けることはできません。開始の値をわざと CRC にしていないのは、CRC-32 で守られた項目の領域に対する CRC-32 は、その中身にほとんど依存しないからです。

**エントロピーワード。** マイコンの定義は、エントロピーワードの出どころを宣言します（`[boot.record] entropy`）。領域だけでは以前の状態に戻ることがあります（`survives = reset-cleared` の電源投入後のすべてゼロや、同じ段階の別のレイアウトの書き手がリングを消した後）。そのため、このワードは新しい並びごとに最小エントロピーを 16 ビット以上持たなければなりません。これを満たすものならどれでも有効です。ハードウェアの乱数生成器、リングオシレータのランダムなビットの繰り返しサンプル、低速と高速のオシレータの周期のキャプチャ、内部センサの ADC の繰り返し変換の下位ビットなどです。出どころの無いマイコンには、ブート記録はありません。

**stage0 の持ち分。** 書き手は記録するすべての段階で動き、stage0 も含まれます。そのため、その時間はその段階の時間の上限（stage0 では `stage0.max_ms`）に数えます。開くときにスロットごとの CRC 1 回、新しい並びでリングの消去、イベントごとに追記 1 回です。stage0 はブートごとにわずかなイベントしか記録しません。stage0 のリングは 2 から 4 スロットで足ります。

### 2.4 引き渡し

段階は、ジャンプのときに 4 つの 32 ビットのレジスタでブートの識別を次の段階に渡します。保持メモリは決して使いません（ハングした前のブートが古い値を残すことがないように）。

| ワード | 値 |
|---|---|
| 0 | `0x52424744`（`DGBR`） |
| 1 | `boot` |
| 2 | `boot tag` |
| 3 | ビット 0-7 `opener`、ビット 8-15 記録のレイアウト、ビット 16-31 はワード 0 から 2 とワード 3 のビット 0-15（リトルエンディアン）に対する CRC-32 の下位 16 ビット |

受け取る段階がこれを使うのは、マジック、検査、レイアウトが一致し、`opener` が自分の番号より小さいときだけです。別のレイアウトの正しい形の引き渡しを受け取った段階は、それをそのまま次に渡します（途中に別のレイアウトの段階が 1 つあっても、つながりが切れないように）。それ以外のときは、自分のブートを渡します。この記録より古い段階は、次の段階が自分でブートを開始するに任せます。

### 2.5 読み手

エージェントは、起動時に 1 つのレイアウトで領域を 1 度読みます（書くことはありません）。書き手ごとに、最新から 2^24 以内の有効な項目を古い順に読みます。実行は、各 `start` の項目か、ブートの変わり目で始まります。書き手ごとに**窓**（`from` = 手元でいちばん古い `eseq` と、その項目が `epoch` を持つかどうか。持つなら、この並びにそれより前のものはありません）と、欠けた連番の範囲ごとの**ギャップ**を示します（飛びの後では、ギャップの中の番号は使われなかったことがあります）。有効な項目が無い書き手は**空**と示します。

ブートは、すべての書き手の実行の順を合わせて順序づけ、1 つの開始者のブートは番号で順序づけます。

- 開始者のいまの並び（手元の最新の項目のタグ）のブートは、ほかのどの並びのブートよりも新しいものです。
- いまの並びの中では、手元の最新の項目から後ろへの距離で順序づけます（それより 2^24 先までのブートは新しいものです。その項目は壊れています）。
- ほかの並びの中では、離れ方が 2^30 未満のときに連番の順で順序づけます（番号で順序づけるのは、どの書き手の実行の順でも関係づけられない組だけです）。
- ほかの 2 つの並びのブートや、ほかの並びで 2^30 以上離れたブートは、番号では順序づけません。

読み手は、新しいブートを古いブートより先に報告することはありません。順序づけられない組は、不確かと印を付けます（両方のブートに `uncertain`）。そのような組は、どの書き手の順でも関係づけられない異なる開始者のブート（2.7）か、もういまの並びでない 1 つの開始者の並びのブートです。

リプレイ: ブートは古い順、ブートの中では書き手の順、次に並びの順です。各イベントは、そのカタログのイベントとして `replayed: true` と識別子 `(writer, tag, eseq)` を付けてリプレイします。ブートは `(opener, boot, boot tag)` です。欠けの報告も一緒にリプレイします。`plan`、`commit`、`self_check`、`confirm` はこの記録を読みません。`app.trial_started` と `app.rolled_back` は状態ログから来ます。

### 2.6 受け手

リプレイは少なくとも 1 回です。手元のすべての項目を、起動のたびにリプレイします。あるリプレイに無かった識別子は二度とリプレイされません。そのため、受け手は `(layout, writer, tag, eseq)` を読んだ前回のリプレイと比べて重複を除けばよく、それより古いものを持つ必要はありません。書き手は、以前に追記した識別子を追記しません（2.3 の手順 3 は壊れた項目を飛び越えます。新しい並びには新しいタグがあります）。そのため、2.7 の限界の中で、新しいイベントを見たものと取り違えることはありません。`from` が受け手がその書き手から最後に見た識別子より後である窓、ギャップ、`epoch` の開始は、そのあいだの項目の欠けです。

### 2.7 主張の限界

- **2^32 の一周。** 識別子が繰り返すのは、1 つの並びで書き手が 2^32 回追記した後だけです。1 つの書き手の追記で 2^32 − `slots` 回より離れた 2 つのリプレイを読む受け手は、新しい項目と同じ番号の古い項目を区別できません。同じように、開始者の追記で 2^32 − `slots` 回より古いブートへの、後の段階のつながりは、最近のブートとして置かれることがあります。また、開始者がもう持っていない並びの 2 つのブートが、その追記で約 3·2^30 回以上離れていて、どの書き手の実行の順でも関係づけられないときは、順序を間違えることがあります（2^32 をまたぐ連番の順では、そのような組は逆向きに 2^30 未満の離れ方に見えます。2.5）。
- **繰り返しの破壊。** 書き手が書いていないバイトが、前回から `slots` 個の項目を追記する前に、最新の項目をまた壊すと、2.3 の飛びでは足りず、書き手が壊れた項目の番号を使い回すことがあります（その欠けは示されません）。最初の一周のあいだにスロットをすべてゼロにする破壊は検出しません。
- **開始者の交代。** 1 つの書き手が読み手のレイアウトでの記録をやめ、また始めるとき（あいだに古いか別のレイアウトの stage0 があるとき）、それが開始したブートと、次の段階が自分で開始したブートは、互いに順序づけられません。読み手はこれを不確かと印を付けます。順序づけるには両方の段階が書くカウンタが必要で、書き手の独立性がそれを許しません。
- **分かれたブート。** チェーンの途中にこの記録より古い段階があるとき、または 1 つのブートに 2 つの記録のレイアウトの段階があるときは、後の段階がブートをもう一度開始することがあります。そのブートは 2 つとしてリプレイされます。

### 2.8 VERSION

0x20（ブート記録の要約）: `layout u8, boots u8, flags u8`（ビット 0: あるブートが不確か。ビット 1: 欠けが示されている、つまりある書き手にギャップか、いちばん古い項目が `epoch` の開始でない窓がある）、続いていちばん新しいブートの `opener u8, boot u32 LE, boot tag u32 LE, count u8` と、そのブートの書き手ごとの最後の項目を `writer u8, format u8, kind u8,
payload[3]` として。0x21 は領域を生で返します。`offset u16` と、最大 `RECORD_PAGE(link)` バイトです。ホストがページをつなぎ、この読み手で解読します。

### 2.9 バージョン付け

レイアウト *n*（1 から 15）は `0xB0 | n` でコミットし、その CRC は *n* を初期値にします。15 を超えるレイアウトは、`0x00` でも以前のどのレイアウトの値でもないコミット値を取り、ここに挙げます。読み手は、最初のバイトが別のレイアウトのコミットであるスロットを数え（刻みが違うところでは近似の数です）、別のレイアウトの記録があることを報告できますが、解読はしません。書き手のイベントの符号化は、その書き手の `event` の番号とともに変わり、番号は各項目にあります。

## 3. ロックアップヒューズ（`boot-record` 1）

### 3.1 セル

サンドボックスの呼び出しを動かすイメージの種類ごとに、セルが 1 つあります。ブートコアのセルとアプリのセルです（アプリとリレーのレイヤーは共有します。コアごとに、開いているサンドボックスの呼び出しは最大 1 つです）。セルは、武装のスロットとそれに続く記録のスロットです（`[boot.record] fuse` が、記録の隣に両方のセルとそのスロットの数を宣言します）。セルにストアするのは、そのセル自身のレイヤーだけです。どのレイヤーの起動も、すべてのセルを読みます。

### 3.2 ヒューズの id

`SHA-256("dagon-fuse/1" ‖ layer u8 ‖ slot u32 LE ‖ image header digest
[32] ‖ chain index u32 LE ‖ artifact SHA-256 [32])`。欄の幅は固定なので、異なる 2 つの呼び出し箇所が同じ入力になることはありません。スロットや拡張の数に上限はありません。拡張の新しいビルドや新しいイメージは、新しい id です。

### 3.3 記録

40 バイトです。

| オフセット | 大きさ | 欄 |
|---|---|---|
| 0 | 1 | 印: `0xA1` 武装、`0xA2` トリップ、`0xA3` クリアの要求、`0xA4` ロックアップの判定、`0xA5` 正常の判定、`0xA6` クリア済み。ほかの値は空き |
| 1 | 1 | レイヤー |
| 2 | 2 | ゼロ |
| 4 | 32 | ヒューズの id |
| 36 | 4 | `[1]` とそれに続くバイト 1 から 35 に対する CRC-32 |

記録は、記録の項目と同じように（印に `0x00`、バイト 1 から 39、最後に印）空きのスロットに書きます。スロットを空けるのは、印への `0x00` の 1 回のストアです。印は CRC の外にあるので、トリップをクリア済みの記録に変えるのは 1 バイトです。

### 3.4 呼び出し

サンドボックスの呼び出しの前に、レイヤーはウォッチドッグに給餌し、武装のスロットに武装の記録を書きます。戻りの経路の最初のストアが、超過や故障の後でも、武装のスロットを空けます（武装解除）。呼び出しが戻ったのは、武装解除がストアされたときです。どの呼び出しの持ち時間もウォッチドッグの周期よりずっと短いので（lifecycle-events.md の 10 節）、呼び出しが武装された状態のウォッチドッグのリセットは、その呼び出しがロックアップしたことを意味します。起動が `can_arm = false` を報告したレイヤーは、その実行では何も武装しません。

ヒューズには**ウォッチドッグのフラグ**が要ります。ウォッチドッグのリセットで立ち、電源投入以外のそれ以降のリセットでも残り、起動が確認したときだけ消えるものです。起動が確認するのは、ストアすべきものをすべてストアしたとき（`complete`）です。マイコンの定義は、マイコンがそのようなフラグを持つかどうかと、その出どころを宣言します（`[watchdog] flag`: リセットのフラグがクリアまで残るハードウェアのレジスタか、マイコンのパッケージが用意するフラグ。例えば、ウォッチドッグのリセットで立てる保持のレジスタ）。これが無いマイコンにはヒューズがありません。定義の読み込みがヒューズを使えないものとして報告し、レイヤーはロックアップヒューズなしでサンドボックスの呼び出しを動かします。

### 3.5 起動

各レイヤーの起動は、拡張を動かす前に、まず終わったものを空け（手順 3）、判定やトリップの場所を作り、その後で次のことをします。

1. **分類。** 武装のスロットが武装されていて、どのセルにも判定が無いほかのセルごとに、自分のセルに判定をストアします。ウォッチドッグのフラグが立っていれば*ロックアップ*、立っていなければ*正常*です。場所が無ければ、`complete` と `can_arm` は false です。
2. **自分の呼び出し。** 自分の武装のスロットが武装されているとき、判定がそう言うとき、または判定が無くウォッチドッグのフラグが立っているときに、ロックアップしたものとします。ロックアップした呼び出しの id がインストールされていれば、トリップの記録を得て（重複なし）、その後で武装のスロットを空けます。場所が無ければ、武装のスロットは武装のままで、`can_arm` と `complete` は false です。ロックアップした呼び出しの id がインストールされていなければ、古いものとして記録して空けます。正常な呼び出しは、ただ空けます。
3. **自分の記録**（上のとおり、最初に行います）。id がインストールされていないトリップは古いものです。このレイヤーが空けます。ほかのセルにクリアの要求があり、自分のクリア済みが無いトリップは、クリア済みになります（1 バイト）。クリアの要求は、ほかのセルがそのクリア済みを持つとき、またはほかのセルがそのトリップを持たないときに空けます。クリア済みは、ほかのセルがその要求を持たないときに空けます。判定は、ほかのセルの武装のスロットがその id を持たないときに空けます。
4. **結果。** インストールされているトリップは、その実行で無効にします。ほかのセルに判定がある id は保留します（この実行では武装しません）。ほかのセルのトリップは報告し、それに基づいて動くことはありません。

そのため、アプリやリレーのロックアップは、ブートコアの起動をそのまま通り抜け（ブートコアは自分のセルに判定をストアするだけです）、アプリの起動がトリップします。ブートコアのロックアップは、ブートコアの次の起動がトリップします。武装、呼び出し、戻り、武装解除のどのバイトでのリセットも、戻った呼び出しをトリップしません。起動中のリセットはフラグと武装の記録を残すので、次の起動が同じ判断を繰り返します。

### 3.6 クリア

DAGON には、トリップをクリアする要求がまだありません。プロトコルにも CLI にもありません。形式のモデルが要求について持っているのは次のことです。エージェントは、自分のセルのアプリのトリップを空けるか、ブートコアのトリップに対してクリアの要求をストアします。ブートコアの次の起動がトリップをクリア済みに変え、双方は相手のものを見たときに自分の記録を空けます。1 つの要求は 1 つのトリップをクリアします。id がインストールされているトリップをクリアするものは、ほかにありません。

### 3.7 主張の限界

電源投入はウォッチドッグのフラグを消します。まだ分類していないロックアップは失われますが、偽造はされません。外来のバイトも同じように記録を壊すことがあります。正常の判定が壊れると、その後のウォッチドッグのリセットが、その中断された呼び出し（戻らなかったもの）をロックアップと分類します。クリア済みの記録が壊れると、まだ残っているクリアの要求が、同じ拡張の次のトリップをもう 1 度クリアします。セルがいっぱいになると、ホストがトリップをクリアするまで、そのレイヤーは何も武装しません。

### 3.8 バージョン付け

ヒューズのレイアウトはそれぞれ 6 つの印の値を持ち、ほかのどのレイアウトの値とも `0x00` とも違います。レイアウト 1 は `0xA1` から `0xA6` を使い、後のレイアウトはその値をここに挙げます。CRC はレイアウトの番号を初期値にします。別のレイアウトの記録は、この読み手には空きのスロットで、それに基づいて動くことはありません。

## 4. マイコンの識別

`identity(id)` は、`SHA-256("dagon-mcu/" ‖ id)` の最初の 8 バイトをリトルエンディアンの u64 にしたものです。`id` はマイコンの定義の `id` です。どの運び手も 64 ビットすべてを持ちます。運び手: `image-header`、`identity-reply`、`version-0x06`、`topology-node`（モデルの `identity::CARRIERS`。テストがこの行と照合します）。定義の読み込みは、どれかの運び手の幅で識別が一致する 2 つの定義を、両方の id を示して受け付けず、運び手の幅ですべてゼロかすべて 1 の識別を受け付けません。読み込んだどの定義とも完全には一致しない識別のデバイスは、不明と表示します。数値のマイコンの表はありません。

## 5. コンパイル済みの構成

### 5.1 本体（`topology-bin` 1）

先頭は 16 バイトです。マジック `DGTP`、レイアウト u16 LE（1）、ノードの数（1 から 8）、リンクの数（≤ 7）、制約の数（≤ 16）、ゼロ 7 バイト。続いて次のものです。

- ノードは各 40 バイト: 番号、役割、ポートの種類、試行の上限、待ち受けの窓 ms u16 LE、マップの id、順番、復旧の段階 [3]、ゼロ 5 バイト、オフセット 16 にマイコンの識別 u64 LE、オフセット 24 にターゲットのタグ [16]。
- リンクは各 16 バイトで、イメージのツールのリンクのレイアウトです。
- 制約は各 16 バイトで、マニフェストの制約のレイアウトです。

正規の形: ノードの `index` は位置と同じ、リンクは `to` の順、予約のバイトはゼロです。デコーダは符号化し直して比べます。ホストの `host.topology.pushed` と親機の `relay.children_set` は、本体の SHA-256 を持ちます。

### 5.2 親機での保存

TOPOLOGY の領域は、同じ大きさで別々に消去できる 2 つのバンクです。各バンクは 64 バイトのヘッダで始まります。

| オフセット | 大きさ | 欄 |
|---|---|---|
| 0 | 1 | コミット: `0xC1`（保存のレイアウト 1） |
| 1 | 3 | ゼロ |
| 4 | 4 | 連番 u32 LE |
| 8 | 4 | 本体の長さ u32 LE |
| 12 | 32 | 本体の SHA-256 |
| 44 | 4 | `[1]` とそれに続くバイト 1 から 43 に対する CRC-32 |
| 48 | 16 | ゼロ |

バイト 1 から 3 と 48 から 63 はゼロとして書き込み、読み手は確かめません（バイト 1 から 3 は CRC の対象です）。

その後に本体が続きます。バンクが数えられるのは、コミットバイトが `0xC1` で、長さが収まり、CRC が一致し、本体の SHA-256 がヘッダのものと同じときです。コピーは、数えられるバンクのうち連番が新しいもの（連番の順）です。数えられるバンクが無ければ、コピーはありません。

**書き込み**（イメージのライフサイクル `written`、ターゲット TOPOLOGY）: ホストは、バンクの容量より大きい本体を、1 バイトも送る前に拒み、親機も消去の前にもう一度拒みます。それ以外のとき、親機はコピーでないバンク（コピーが無ければバンク 0）に、連番 = コピーの連番 + 1（無ければ 1）で書きます。バンクを消去し、本体を書き込み、ヘッダのバイト 1 から 63 を書き込み、コミットバイトを書き込みます。書き込みのステップを 0 から、消去または書き込みの 1 バイトごとに 1 つ数えると、コミットバイトはステップ `bank size + body
length + 63` です。そのステップが終わる前に止まった書き込みは、前のコピーを 1 バイトも変えず残します。終わった後は新しいコピーです。その後の読み出しは、次の書き込みまで同じ答えを返します（1）。書き込みが終わると、前のコピーには届かなくなります。遷移は、コピーが無かったときは `Absent → Written`、それ以外は `Written → Written` です。

**読み出し**はリレーの起動時です。本体を解読できないコピー（親機が読まないレイアウトの番号や、不正な形）は無いものとして読み、プロジェクトの予備の一覧を使います（`relay.children_set { source: Fallback }`）。本体は全部適用するか、まったく適用しないかです。

モデルは、すべてのシナリオのすべての操作の後でこれらを確かめます。`tests/fixed.rs` の固定のケースは、守る性質を名前で示します。

| Id | 性質 |

| P1 | 手元のすべての項目を、そのレイアウトのすべてのアプリがリプレイします。 |

| P5 | 読み手は、新しいブートを古いブートより先に報告しません。順序づけられない組には不確かと印を付けます。組ごとに、順序のない組は、開始者が異なるか、1 つの開始者の 2 つの並びか、1 つの開始者の 2^30 以上離れた番号です。 |

## 7. ブートコアのトライアルのセル

stage0 は、待機中のブートコアの起動の回数を、フラッシュではなく 2 つの保持のワードで数えます。こうすると stage0 にはフラッシュの書き手がなく（stage0 は入れ替えないので、持つコードをできるだけ減らします）、書き手の不具合が、何も起動しない stage0 に変わることはありません。`dagon_core::bootcore` がコーデックで、そのテストが証明です。

| マイコン | 場所 | 残るもの | 失うもの |
|---|---|---|---|
| RP2040 | ウォッチドッグの SCRATCH0、SCRATCH1（ブート ROM は SCRATCH4-7 を使います） | 電源投入と RUN ピン以外のすべてのリセット | 電源 |
| STM32F401RE | RTC のバックアップレジスタ BKP0R、BKP1R | ウォッチドッグのものを含むすべてのシステムリセット | バックアップドメインの電源（VBAT を結んでいるところでは VDD） |

待機中のイメージ `p` の起動 `n`（最大 15）の値は、1 つのワード `0xB7 << 24 | p.digest16[0] << 16 | p.digest16[1] << 8 | n << 4 | (!n &
0xF)` で、両方の場所にストアします。ワードが `p` について数えられるのは、タグ、ダイジェストのバイト、回数の検査（下位 4 ビットは回数の補数）が成り立つときだけです。セルは 2 つのワードの回数の大きいほうを数え、`[0, 0]` はクリアされたセルです。ワードはそれぞれ 1 回のストアなので、リセットが 2 つのあいだに来ることがあります。その場合、新しいワード 1 つと古いワード 1 つでも新しい起動を数え、少なくなることはありません（モデルは、以前の形であるワードとその補数では、そのような組を 0 と読み、起動を失うことを見つけました）。ランダムなワードが一致する確率は 2^-28 で、一致しても stage0 がそのコアを早くあきらめるだけです。

実行可能なモデルは `dagon-retained-model` の `world_trial` です。本番のコーデックと、stage0 とブートコアの決まり（`bootcore::choose`、`settle`）を、2 つのワードの上で動かします。新しいコアは良いものか壊れたものとして待機にし（壊れたコアは stage0 の検査を通り、自分の検査に失敗します）、セルへのどのストアの後にも（セルの検査のものを含み、マイコンの順に、ワード 0、次にワード 1）、リセットか電断（セルはクリアかランダムになります）を入れます。`cargo test` では 10,000 のシードのシナリオ、完全なプロファイルでは 1,000,000 です。その性質を、すべての操作の後で確かめます。

| Id | 性質 |
|---|---|
| C1 | 2 回の電断のあいだに、待機中のコアをトライアルとして起動するのは最大 `max` 回です。 |
| C2 | それ以上の故障が無ければ、最大 `max + 1` 回のブートでトライアルが終わります。待機中のコアは無く、あるコアが動きます。 |
| C3 | 壊れたコアが確定することはありません。 |

マイコンのパッケージのスイープ（`a_power_cut_at_every_flash_step_leaves_a_bootable_core`）は、フラッシュの側を足します。入れ替えのすべてのフラッシュ操作での電断で、状態ログのコンパクションも含みます。書いたものをまったく保持しないセルは、起動したブートコアとアプリが実行する `bootcore::cell_holds` が見つけます。そのようなノードはブートコアを受け取らず、それに気づいた待機中のコアは自分で元に戻ります。回数を持つワードがあるセルは stage0 が書いたものなので保持しており、検査はその上に何も書きません。何も数えていないセルにだけ、試しの値（セルのワードが取らない値）と元の値を、ワードごとに書き、それぞれ読み返します。そのため、検査の中でのリセットで、セルの数える起動が少なくなることはありません（モデルは、数えている途中に試しの値を書いた以前の検査では、失敗するコアが終わりなく起動できることを見つけました）。

主張の限界: それぞれの場所が、挙げたリセットをまたいで値を保つことは、ベンダーが文書で示している動作で、ボードごとに確かめる必要があります。
